## Why a queue exists: decoupling in three dimensions

Putting a broker between producer and consumer buys you three separations, and every use of a
queue is one of them:

- **In time** — the producer does not wait for the consumer. A 400 ms email send becomes a
  2 ms enqueue.
- **In rate** — a spike is absorbed as backlog instead of as errors. The queue is a shock
  absorber.
- **In topology** — one event, many consumers, none of whom the producer knows about.

```python
def synchronous(request_ms, side_effects):
    return request_ms + sum(side_effects.values())

def queued(request_ms, side_effects, enqueue_ms=2):
    return request_ms + enqueue_ms * len(side_effects)

effects = {"send email": 400, "update search index": 120, "notify webhooks": 250,
           "recompute feed": 300}
print(f"synchronous p50: {synchronous(30, effects)} ms")
print(f"with a queue:    {queued(30, effects)} ms  (work still happens, just not on the request)")
print(f"user-visible saving: {synchronous(30, effects) - queued(30, effects)} ms")
```

```output
synchronous p50: 1100 ms
with a queue:    38 ms  (work still happens, just not on the request)
user-visible saving: 1062 ms
```

The work does not disappear — it moves off the request path, where the user is waiting, onto a
worker pool, where nobody is. That is the entire value proposition, and it comes with a price:
the user gets a response before the work is done, so every consumer must be safe to retry
(ch. 21) and the system is now eventually consistent (ch. 16).

## Queue versus log: the distinction that decides your broker

```python
class Queue:
    """Competing consumers. A message is delivered once and then it is gone."""
    def __init__(self): self.items = []
    def push(self, m): self.items.append(m)
    def pop(self):
        return self.items.pop(0) if self.items else None

class Log:
    """Append-only. Consumers hold their own offset; messages stay until retention expires."""
    def __init__(self): self.records, self.offsets = [], {}
    def append(self, m): self.records.append(m); return len(self.records) - 1
    def read(self, group, n=1):
        off = self.offsets.get(group, 0)
        batch = self.records[off:off + n]
        self.offsets[group] = off + len(batch)
        return batch

q = Queue()
for m in ("a", "b", "c"): q.push(m)
print("queue:", [q.pop(), q.pop(), q.pop(), q.pop()])

log = Log()
for m in ("a", "b", "c"): log.append(m)
print("log, billing group :", log.read("billing", 3))
print("log, analytics grp :", log.read("analytics", 3), "<- same records, own offset")
```

```output
queue: ['a', 'b', 'c', None]
log, billing group : ['a', 'b', 'c']
log, analytics grp : ['a', 'b', 'c'] <- same records, own offset
```

RabbitMQ, SQS, and Celery are **queues**: the broker tracks per-message state and the message
is deleted on ack. Kafka, Kinesis, and Redpanda are **logs**: the broker tracks nothing but an
offset per consumer group, records are immutable, and a new consumer can replay history from
the beginning. Replay is the feature that makes logs the backbone of event-driven
architectures (ch. 18) — you can add a consumer built next year and feed it last year's
events.

## Partitions give you ordering *per key*, and parallelism across keys

A single ordered log does not scale: one consumer, one core. Split it into partitions, route
by key, and you get ordering where it matters and parallelism everywhere else.

```python
import hashlib
from collections import defaultdict

class PartitionedLog:
    def __init__(self, n_partitions):
        self.parts = [[] for _ in range(n_partitions)]
        self.offsets = defaultdict(lambda: [0] * n_partitions)

    def partition_for(self, key):
        return int(hashlib.md5(str(key).encode()).hexdigest(), 16) % len(self.parts)

    def append(self, key, value):
        p = self.partition_for(key)
        self.parts[p].append((key, value))
        return p

    def poll(self, group, partition, n=10):
        off = self.offsets[group][partition]
        batch = self.parts[partition][off:off + n]
        self.offsets[group][partition] = off + len(batch)
        return batch
log = PartitionedLog(4)
events = [("order:7", "created"), ("order:3", "created"), ("order:7", "paid"),
          ("order:12", "created"), ("order:7", "shipped"), ("order:3", "cancelled")]
for k, v in events:
    print(f"append {k:9} {v:10} -> partition {log.append(k, v)}")

print()
for p in range(4):
    if log.parts[p]:
        print(f"partition {p}: {[f'{k}:{v}' for k, v in log.parts[p]]}")
```

```output
append order:7   created    -> partition 0
append order:3   created    -> partition 1
append order:7   paid       -> partition 0
append order:12  created    -> partition 2
append order:7   shipped    -> partition 0
append order:3   cancelled  -> partition 1

partition 0: ['order:7:created', 'order:7:paid', 'order:7:shipped']
partition 1: ['order:3:created', 'order:3:cancelled']
partition 2: ['order:12:created']
```

Every `order:7` event landed in the same partition, in the order it was produced, so a
consumer sees `created`, then `paid`, then `shipped`, and never a shipment before a payment.
Across partitions there is no ordering at all — and that is the trade you accept for
throughput.

### Consumer groups: parallelism with exactly one owner per partition

```python
def assign(partitions, consumers):
    """Round-robin partition assignment, the shape every rebalance protocol produces."""
    out = defaultdict(list)
    for p in range(partitions):
        out[consumers[p % len(consumers)]].append(p)
    return dict(out)

for n in (1, 2, 3, 8):
    consumers = [f"c{i}" for i in range(n)]
    print(f"{n} consumers over 4 partitions: {assign(4, consumers)}")
```

```output
1 consumers over 4 partitions: {'c0': [0, 1, 2, 3]}
2 consumers over 4 partitions: {'c0': [0, 2], 'c1': [1, 3]}
3 consumers over 4 partitions: {'c0': [0, 3], 'c1': [1], 'c2': [2]}
8 consumers over 4 partitions: {'c0': [0], 'c1': [1], 'c2': [2], 'c3': [3]}
```

Two rules fall out. **Consumers beyond the partition count sit idle** — partition count is
your maximum parallelism, so choose it generously up front (it is painful to change, because
changing it rehashes keys onto different partitions). And during a rebalance, ownership moves;
in-flight work must be idempotent or committed before the handover.

## Delivery semantics: pick your poison

| Guarantee | How it is implemented | What it costs |
|---|---|---|
| at-most-once | ack before processing | fast; loses messages when a consumer crashes |
| at-least-once | ack after processing | never loses; delivers duplicates after a crash |
| exactly-once | transactional offset commit | expensive, and only inside one system's boundary |

**At-least-once plus idempotent consumers is the answer in practice.** True exactly-once
delivery across a network is impossible — the ack itself can be lost — so "exactly-once" in
Kafka means *exactly-once processing within Kafka's own transaction boundary*, which does not
extend to the email you sent or the row you wrote in Postgres.

```python
processed = set()          # in production: a table with a unique index on message_id

def handle(msg_id, payload, charged):
    if msg_id in processed:
        return "duplicate, skipped"
    processed.add(msg_id)
    charged.append(payload)
    return "processed"

charged = []
delivery = [("m1", 5.0), ("m2", 9.0), ("m1", 5.0), ("m3", 2.0), ("m2", 9.0)]  # broker retries
for mid, amount in delivery:
    print(f"{mid}: {handle(mid, amount, charged)}")
print(f"total charged: {sum(charged)} (correct: 16.0)")
```

```output
m1: processed
m2: processed
m1: duplicate, skipped
m3: processed
m2: duplicate, skipped
total charged: 16.0 (correct: 16.0)
```

The deduplication key must be the *producer's* id, generated once and carried through every
retry. A broker-assigned id changes on redelivery and buys you nothing.

## Backlog arithmetic: Little's law again

Queue depth is not a health metric on its own — **age of the oldest message** is. But the
relationship between arrival rate, service rate, and drain time is simple arithmetic you
should be able to do in your head.

```python
def backlog(arrival_qps, workers, per_msg_s, burst_s, burst_multiplier):
    capacity = workers / per_msg_s
    peak = arrival_qps * burst_multiplier
    built = max(0.0, (peak - capacity)) * burst_s
    drain = built / (capacity - arrival_qps) if capacity > arrival_qps else float("inf")
    print(f"capacity {capacity:6.0f}/s | peak {peak:6.0f}/s | backlog after burst "
          f"{built:8,.0f} msgs | drains in {drain/60:6.1f} min" if drain != float("inf")
          else f"capacity {capacity:6.0f}/s | peak {peak:6.0f}/s | NEVER DRAINS")

backlog(1_000, workers=40, per_msg_s=0.02, burst_s=300, burst_multiplier=3)
backlog(1_000, workers=80, per_msg_s=0.02, burst_s=300, burst_multiplier=3)
backlog(1_000, workers=20, per_msg_s=0.02, burst_s=300, burst_multiplier=3)
```

```output
capacity   2000/s | peak   3000/s | backlog after burst  300,000 msgs | drains in    5.0 min
capacity   4000/s | peak   3000/s | backlog after burst        0 msgs | drains in    0.0 min
capacity   1000/s | peak   3000/s | NEVER DRAINS
```

Capacity must exceed *average* load with margin, not peak load — the queue absorbs the peak,
as long as it can drain before the next one. A pool sized below average load never recovers,
and that is what an unbounded, growing backlog actually means.

## Retries, dead letters, and poison messages

```python
class Broker:
    def __init__(self, max_attempts=3):
        self.main, self.dlq, self.max_attempts = [], [], max_attempts
    def publish(self, m): self.main.append({"body": m, "attempts": 0})
    def consume(self, handler):
        pending, self.main = self.main, []
        for msg in pending:
            try:
                handler(msg["body"])
            except Exception as e:
                msg["attempts"] += 1
                if msg["attempts"] >= self.max_attempts:
                    msg["error"] = str(e)
                    self.dlq.append(msg)                  # park it, do not block the queue
                else:
                    self.main.append(msg)                 # retry later (with backoff, ch. 21)

def handler(body):
    if body["kind"] == "poison":
        raise ValueError("cannot parse body")
    return True

b = Broker()
for i in range(3): b.publish({"kind": "ok", "i": i})
b.publish({"kind": "poison", "i": 99})
for round_ in range(4):
    b.consume(handler)
    print(f"round {round_}: main={len(b.main)} dlq={len(b.dlq)}")
print("dead letter:", b.dlq)
```

```output
round 0: main=1 dlq=0
round 1: main=1 dlq=0
round 2: main=0 dlq=1
round 3: main=0 dlq=1
dead letter: [{'body': {'kind': 'poison', 'i': 99}, 'attempts': 3, 'error': 'cannot parse body'}]
```

Without a dead-letter queue, that one unparseable message is retried forever, consuming a
worker slot and — in an ordered partition — blocking every message behind it. The DLQ is not
optional plumbing; it is what stops one bad record from halting a pipeline.

## The outbox pattern: never write to two systems at once

The classic bug: commit a row to the database, then publish an event. If the process dies
between them, the database says the order exists and the rest of the world never hears about
it. You cannot fix this with retries — the two writes are not atomic.

```python
db_rows, outbox, published = [], [], []

def create_order_atomically(order, crash_after_commit=False):
    # ONE transaction writes both the row and the event
    db_rows.append(order)
    outbox.append({"type": "OrderCreated", "id": order["id"], "sent": False})
    if crash_after_commit:
        return "crashed before publishing"
    return "committed"

def relay():                       # a separate process tails the outbox
    for e in outbox:
        if not e["sent"]:
            published.append(e); e["sent"] = True

print(create_order_atomically({"id": 1}, crash_after_commit=True))
print(f"rows={len(db_rows)} outbox={len(outbox)} published={len(published)}  <- inconsistent?")
relay()                            # the relay recovers after the crash
print(f"after relay: published={[e['type'] + ':' + str(e['id']) for e in published]}")
```

```output
crashed before publishing
rows=1 outbox=1 published=0  <- inconsistent?
after relay: published=['OrderCreated:1']
```

The event is written *in the same transaction as the data*, so either both exist or neither
does. A relay process (or change-data-capture off the write-ahead log, ch. 18) publishes it
afterwards, at-least-once — which is fine, because consumers are idempotent.

## Try it Yourself

```python
def fanout(followers, posts_per_day=2, feed_opens_per_day=8, authors_followed=200):
    """Fan-out on write vs on read: the classic feed trade (ch. 30)."""
    write_rows = followers * posts_per_day                 # one inbox row per follower per post
    read_merges = followers * feed_opens_per_day           # one K-way merge per feed open
    print(f"{followers:>11,} followers | on-write {write_rows:>14,} inbox rows/day "
          f"| on-read {read_merges:>12,} merges/day of {authors_followed} authors each")

for f in (100, 10_000, 1_000_000, 100_000_000):
    fanout(f)
```

```output
        100 followers | on-write            200 inbox rows/day | on-read          800 merges/day of 200 authors each
     10,000 followers | on-write         20,000 inbox rows/day | on-read       80,000 merges/day of 200 authors each
  1,000,000 followers | on-write      2,000,000 inbox rows/day | on-read    8,000,000 merges/day of 200 authors each
100,000,000 followers | on-write    200,000,000 inbox rows/day | on-read  800,000,000 merges/day of 200 authors each
```

Both columns grow with the follower count, but they differ in *when* and *where* the cost
lands. Fan-out on write turns one post into as many row inserts as you have followers, and
they all arrive in a burst the moment a celebrity posts — 100 million writes from one tap.
Fan-out on read costs nothing at write time and charges every feed open a 200-way merge,
which is steady, cacheable, and paid by the reader. Real systems go hybrid: fan out on write
for ordinary accounts, merge celebrity posts in at read time. Change `posts_per_day` to 20
(a news account) and watch the write column pull away.

```python
def lag_report(log, group, rate_per_s):
    total_lag = 0
    for p, part in enumerate(log.parts):
        end = len(part)
        committed = log.offsets[group][p]
        lag = end - committed
        total_lag += lag
        print(f"  partition {p}: end={end:6,} committed={committed:6,} lag={lag:6,}")
    eta = total_lag / rate_per_s if rate_per_s else float("inf")
    print(f"  total lag {total_lag:,} msgs | at {rate_per_s:,}/s catch-up in {eta:.1f} s")
    return total_lag

log = PartitionedLog(4)
produce_rate, consume_rate, duration = 1_000, 800, 60

for t in range(duration):                       # 60 seconds of production
    for i in range(produce_rate):
        log.append(f"key:{(t * produce_rate + i) % 5000}", "evt")

# consumer group drains at 800/s while producing continues -> it falls behind
consumed = consume_rate * duration
per_part = consumed // 4
for p in range(4):
    log.offsets["workers"][p] = min(len(log.parts[p]), per_part)

print("during the burst:")
lag = lag_report(log, "workers", consume_rate)
print(f"\nproducer stopped. drain at {consume_rate}/s -> "
      f"{lag / consume_rate:.0f} s to catch up ({lag / consume_rate / 60:.1f} min)")
print(f"headroom check: consumer capacity {consume_rate}/s < producer {produce_rate}/s "
      f"-> lag grows {produce_rate - consume_rate}/s while the burst lasts")
```

```output
during the burst:
  partition 0: end=15,108 committed=12,000 lag= 3,108
  partition 1: end=15,036 committed=12,000 lag= 3,036
  partition 2: end=14,592 committed=12,000 lag= 2,592
  partition 3: end=15,264 committed=12,000 lag= 3,264
  total lag 12,000 msgs | at 800/s catch-up in 15.0 s

producer stopped. drain at 800/s -> 15 s to catch up (0.2 min)
headroom check: consumer capacity 800/s < producer 1000/s -> lag grows 200/s while the burst lasts
```

The insight: lag is measured per partition, and the *maximum* partition lag is what matters —
a group can look healthy in aggregate while one partition (a hot key, a slow consumer, a
rebalance that never finished) falls hours behind. Two derived signals belong on the
dashboard: **lag in messages** (is it growing?) and **age of the oldest unconsumed record** (how
stale is the data downstream?). The second one is the one to alert on, because it is expressed
in the units your users experience.
