## What NumPy is, and why it exists

NumPy is a way to store a big pile of numbers so the computer can crunch them fast. That is
the whole job, and it does it by making two promises about the numbers: they are all the
same kind, and they sit right next to each other in memory.

Python lists make neither promise. They are flexible but slow for numerical work: every
element is a **boxed Python object** — a full Python value with its own type tag and
bookkeeping, stored somewhere else in memory — so arithmetic and comparisons have to ask the
interpreter "what are you?" once per element, and nothing is **contiguous** (packed side by
side) in memory.

> **Picture it:** a Python list is a row of envelopes. Each envelope holds a slip saying
> where the real number lives and what kind of thing it is, so reading one number means
> opening an envelope and walking somewhere. A NumPy array is an egg carton: identical
> slots, side by side, holding the numbers themselves. You can scan a carton in one sweep.

NumPy's array type is the **ndarray** ("n-dimensional array") — a block of raw memory
holding **homogeneous** elements (all the same type), processed by compiled C/Fortran code
instead of the Python interpreter. That's the whole story. Every performance advantage
flows from those two decisions: one dtype, contiguous layout.

## Creating arrays and reading their metadata

Every array carries a small label describing its numbers: what kind they are, how many,
and how they are arranged. Reading that label is how you answer "how big is this?" and
"what shape is this?" without printing the data.

```python
import numpy as np

# From a Python list — dtype inferred
a = np.array([1.0, 2.0, 3.0])           # float64 by default (64-bit float)
b = np.array([1, 2, 3], dtype=np.int32) # explicit int32

print("a dtype   :", a.dtype)
print("a shape   :", a.shape)
print("a ndim    :", a.ndim)
print("a size    :", a.size)             # total elements
print("a itemsize:", a.itemsize, "bytes")
print("a nbytes  :", a.nbytes, "bytes")  # = size * itemsize
```

```output
a dtype   : float64
a shape   : (3,)
a ndim    : 1
a size    : 3
a itemsize: 8 bytes
a nbytes  : 24 bytes
```

Read the output top to bottom: the **dtype** is the kind of number in every slot
(`float64`, a 64-bit decimal number); the **shape** `(3,)` says "one axis, 3 long"; `ndim` is
the number of axes; `size` is the total count of elements; `itemsize` is the bytes per
element; and `nbytes` is the bytes for the whole thing.

`nbytes = size × itemsize`. Here that is 3 numbers × 8 bytes = 24 bytes. A float64 is 8
bytes; a float32 is 4. Choosing the right dtype cuts memory in half and often halves
compute time (more data fits in cache — the CPU's small, very fast memory, covered below).

> **In plain words:** the size of an array in memory is just "how many numbers" times "how
> big each number is". Halve the size of each number and the whole array halves.

## The dtype is everything

A dtype is a promise about what every slot can hold. A small dtype is cheap but can only
hold a small range of values; a big dtype holds more but costs more memory.

NumPy's type hierarchy starts with four families: integers, unsigned integers (whole
numbers that can't be negative), floats (numbers with a decimal point), and booleans. The
suffix is the bit width — how many bits (0/1 switches) each number gets: `int8` has 8 bits,
`float32` has 32.

```python
import numpy as np

dtypes = [np.int8, np.int16, np.int32, np.int64,
          np.float16, np.float32, np.float64, np.bool_]

for dt in dtypes:
    info = np.iinfo(dt) if np.issubdtype(dt, np.integer) else (
           np.finfo(dt) if np.issubdtype(dt, np.floating) else None)
    size = np.dtype(dt).itemsize
    if info is not None:
        rng = f"[{info.min}, {info.max}]" if hasattr(info, 'min') else f"eps={info.eps:.2e}"
        print(f"{dt.__name__:<12} {size} bytes  range: {rng}")
    else:
        print(f"{dt.__name__:<12} {size} bytes")
```

```output
int8         1 bytes  range: [-128, 127]
int16        2 bytes  range: [-32768, 32767]
int32        4 bytes  range: [-2147483648, 2147483647]
int64        8 bytes  range: [-9223372036854775808, 9223372036854775807]
float16      2 bytes  range: [-65504.0, 65504.0]
float32      4 bytes  range: [-3.4028234663852886e+38, 3.4028234663852886e+38]
float64      8 bytes  range: [-1.7976931348623157e+308, 1.7976931348623157e+308]
bool         1 bytes
```

Each line shows the bytes per element and the **range** — the smallest and largest value
that fits. `int8` gets 8 bits, which is $2^8 = 256$ patterns, so it covers $-128$ to $127$.
Each extra byte multiplies the range enormously. Floats reach much further for the same
bytes (`float32` tops out near $3.4 \times 10^{38}$), but notice `float16`: its largest
value is only 65504.

Range is only half the story for floats. What they really trade away is **precision**,
measured by **eps** (machine epsilon) — the gap between 1.0 and the next number the type
can represent. `np.finfo(np.float16).eps` is about `9.77e-04` (roughly 3 trustworthy decimal
digits), float32's is `1.19e-07` (about 7 digits), and float64's is `2.22e-16` (about 16).
`bool` uses a whole byte per True/False, not one bit.

> **Picture it:** integer dtypes are rulers of different lengths — a longer ruler measures
> bigger things. Float dtypes are rulers with finer or coarser tick marks — finer ticks
> measure more precisely.

> **Watch out:** integer arithmetic that overflows its dtype silently wraps around: in
> `int8`, `100 + 100` comes out as `-56`, with no error. Storing pixel values (0–255) in
> `int8` instead of `uint8` is a classic version of this bug.

**Rule of thumb:** use float32 for model weights / training data (halves RAM vs float64,
GPU-native — graphics cards are built to crunch 32-bit floats). Use float64 for intermediate
statistics where precision matters (long sums and variances lose digits in float32). Use
int32/int64 for indices; int8/uint8 for image pixel data.

## 2-D arrays and shapes

A 2-D array is a table: rows and columns. Its shape is written `(rows, cols)`, and the
same numbers can be re-arranged into a different table shape without moving them.

```python
import numpy as np

# shape (rows, cols)
M = np.array([[1, 2, 3],
              [4, 5, 6]], dtype=np.float64)   # shape (2, 3)

print("shape  :", M.shape)
print("ndim   :", M.ndim)
print("size   :", M.size)                     # 2 * 3 = 6
print("nbytes :", M.nbytes)                   # 6 * 8 = 48 bytes

# Reshape never copies as long as layout allows
v = M.reshape(6)     # flatten to 1-D, still the same memory
v2 = M.reshape(3, 2) # 3 rows, 2 cols
print("reshaped:", v2.shape)
```

```output
shape  : (2, 3)
ndim   : 2
size   : 6
nbytes : 48
reshaped: (3, 2)
```

The shape `(2, 3)` means 2 rows and 3 columns, so `size` is $2 \times 3 = 6$ and `nbytes` is
6 × 8 = 48. Reshaping to `(3, 2)` keeps the same 6 numbers and only changes how you index
them — the total must stay 6, or NumPy refuses.

`reshape` returns a **view**, not a copy, whenever the data is contiguous. A view is a new
array object that looks at the *same* memory through a different shape. Modifying `v`
modifies `M`. This is not a bug — it's a feature. Views are free; unnecessary copies are one
of the main sources of accidental memory bloat in NumPy code.

> **Picture it:** a view is a second pair of glasses on the same page. One pair reads the
> numbers as 2 rows of 3, the other as 3 rows of 2. Scribble on the page and both pairs see
> the scribble.

### Memory layout: row-major (C) vs column-major (F)

Memory is one long line of bytes, not a grid. So a table has to be laid out flat
somehow — and there are two natural choices: row after row, or column after column.

NumPy stores 2-D arrays in **row-major** order by default (also called **C order**, after
the C language): the elements of row 0 come first in memory, then row 1, and so on.
**Column-major** (**F order**, after Fortran) stores column 0 first instead. The **strides**
tell you how many bytes to jump to move one step along each axis.

> **Picture it:** a 4×3 table of float32 is really one shelf of 12 boxes, each box 4 bytes
> wide. To step one column to the right, you move one box: 4 bytes. To step one row down,
> you skip a whole row of 3 boxes: 12 bytes. Those two jump sizes are the strides.

```python
import numpy as np

M = np.zeros((4, 3), dtype=np.float32)  # 4 rows, 3 cols, 4 bytes each

print("strides:", M.strides)   # (bytes per row, bytes per element)
print("layout :", "C" if M.flags['C_CONTIGUOUS'] else "F")

M_F = np.asfortranarray(M)     # column-major copy
print("F strides:", M_F.strides)
```

```output
strides: (12, 4)
layout : C
F strides: (4, 16)
```

Row stride = 3 columns × 4 bytes = 12. Column stride = 4 bytes (one element). For the
Fortran layout it flips: 4 bytes per row step, 4×4=16 bytes per column step (in F order,
going one column over means skipping a whole column of 4 elements).

Why does this matter? Your CPU never fetches one number at a time. It pulls a whole chunk
of neighbouring bytes (a **cache line**, typically 64 bytes) into its cache. If your next
read is in that chunk, it is nearly free; if it is far away, the CPU waits for a new chunk —
a **cache miss**. Iterating along the axis where stride is largest (wrong direction) causes
cache misses. Column-by-column iteration on a row-major array is slow; row-by-row is fast.
NumPy operations along `axis=0` (columns) vs `axis=1` (rows) have different performance
profiles — this is why you'll sometimes see a 10× difference just from changing axis order
or transposing first.

> **Picture it:** reading a book line by line, you turn pages rarely. Reading the first
> word of every line on every page, then the second word of every line, you'd be flipping
> pages constantly. Same book, same words — the order of access is what's slow.

## Views vs copies

When you pull part of an array out, NumPy either hands you a window onto the same memory
(a view) or photocopies those numbers into new memory (a copy). Which one you get decides
whether changing the piece also changes the original.

Understanding when NumPy copies is essential for writing fast, bug-free code.

```python
import numpy as np

a = np.array([10, 20, 30, 40, 50], dtype=np.int64)

# Slicing gives a VIEW (same memory)
s = a[1:4]
s[0] = 999          # modifies a!
print("a after slice mutation:", a)

# Fancy indexing gives a COPY (new memory)
idx = np.array([1, 3])
c = a[idx]
c[0] = 0            # does NOT modify a
print("a after fancy-index mutation:", a)

# .copy() forces a new allocation
d = a[1:4].copy()
d[0] = -1
print("a after copy mutation:", a)
```

```output
a after slice mutation: [ 10 999  30  40  50]
a after fancy-index mutation: [ 10 999  30  40  50]
a after copy mutation: [ 10 999  30  40  50]
```

Follow the `999` through the three lines. The slice `a[1:4]` is a view, so setting `s[0]`
wrote straight into `a` — the first line shows `999` in `a`. The fancy-indexed `c` and the
`.copy()` `d` are copies: setting their first element to `0` and `-1` left `a` alone, so the
second and third lines are unchanged (the `999` you still see is from the first step).

The rule: **slices (`:`) give views; fancy indexing (integer arrays, booleans) gives
copies.** **Fancy indexing** means picking elements with a list/array of positions or a
true/false mask instead of a `start:stop` range. Scalar/slice indexing is free; fancy
indexing pays for the allocation (new memory has to be reserved and filled). If you need to
pass data to a function without risking mutation, `.copy()` it first.

> **In plain words:** a slice can be a view because it is a regular pattern — "start
> here, step this many bytes" — which strides can describe. Positions like `[1, 3]` or a
> scattered mask have no single step size, so NumPy has to gather them into new memory.

> **Watch out:** a function that receives a slice and edits it in place edits the caller's
> array too. That is the most common "where did my data change?" bug in NumPy code.

## Recap in plain words

- An ndarray is an egg carton of numbers: one dtype, packed side by side, crunched by
  compiled code.
- `nbytes = size × itemsize`; halving the dtype (float64 → float32) halves the memory.
- Integer dtypes trade range for size; float dtypes trade precision (eps) for size.
- Memory is a flat line; strides say how many bytes to jump per axis. NumPy defaults to
  row-major (C order).
- Walk memory in order (along the small stride) and the cache helps you; jump around and
  you pay for cache misses.
- Slices and most reshapes are views (shared memory, free); fancy indexing makes copies.

## Try it Yourself

```python
import numpy as np

# 1) Play with dtypes and observe nbytes.
for dt in [np.float16, np.float32, np.float64]:
    a = np.ones(1_000_000, dtype=dt)
    print(f"{dt.__name__:<10} {a.nbytes / 1e6:.1f} MB")

# 2) Strides intuition: a transposed array is a view, not a copy.
M = np.arange(12, dtype=np.float64).reshape(3, 4)
T = M.T            # transpose — just flips the strides
T[0, 0] = 999
print("M[0,0] after T mutation:", M[0, 0])   # 999 — same memory

# 3) Contiguous check: T is not C-contiguous, so operations on it may be slower.
print("M contiguous:", M.flags['C_CONTIGUOUS'])
print("T contiguous:", T.flags['C_CONTIGUOUS'])
# Fix: np.ascontiguousarray(T) makes a fresh C-order copy.
```

```output
float16    2.0 MB
float32    4.0 MB
float64    8.0 MB
M[0,0] after T mutation: 999.0
M contiguous: True
T contiguous: False
```

Notice two things in the output. The memory column doubles exactly as the dtype doubles
(2 → 4 → 8 MB for a million numbers). And `M[0,0]` became 999 even though you only wrote
to `T` — a transpose just swaps the strides, so it is a view of the same memory, and that
view is not C-contiguous. Try a `(1000, 1000)` array, or a `uint8` one, and predict
`nbytes` before you run it.

Write code to verify. Then create the array with `np.ones`, check `.nbytes`, and confirm

> **Hint:** multiply rows × columns × bytes per element, then divide by $1024^2$ to get MB.
> For strides, ask: how many bytes to step one column right, and how many to step one row

<summary>Solution</summary>

```python
import numpy as np

for dt, expected_mb in [(np.float64, 8.0), (np.float32, 4.0)]:
    a = np.ones((1024, 1024), dtype=dt)
    mb = a.nbytes / 1024**2
    print(f"{dt.__name__}: {mb:.1f} MB  strides={a.strides}")

# float64: 1024*1024*8 = 8_388_608 bytes = 8.0 MB
# float32: 1024*1024*4 = 4_194_304 bytes = 4.0 MB
```

Row-major strides for (1024, 1024) float64: `(8192, 8)` — move one row = 1024×8 = 8192
bytes; move one column = 8 bytes. For float32 it's `(4096, 4)`. The key insight: memory is
always rows × columns × itemsize, and in row-major layout the row stride is "one whole row
of bytes" while the column stride is "one element".
