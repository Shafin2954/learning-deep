## The profiling-first rule

Before you make code faster, find out *where* it is slow. Guessing wastes time: the slow
part is rarely where you think. Measure first, then fix the biggest problem, then measure
again.

Never optimize before measuring. Two tools:

- **`df.info(memory_usage='deep')`** — shows dtype and memory per column.
- **`%timeit` / `time.perf_counter`** — measures wall time (real elapsed time, as a clock on
  the wall would show it).

Most pandas performance problems fall into four buckets:

1. **Wrong dtype** — `object` column that should be `category`, `int64`, or `float32`.
2. **Using `.apply()`** — a Python loop in disguise.
3. **Unnecessary copies** — chained operations materializing intermediate DataFrames.
4. **Missing `numexpr`** — complex arithmetic that could use compiled expressions.

> **Picture it:** a slow program is a traffic jam. Widening a road that isn't jammed does
> nothing; profiling is the traffic report that tells you which junction to fix.

## Dtype optimization: the biggest win

The cheapest speed-up is storing each column in the smallest type that holds its values.
Text that repeats a handful of values ("alpha", "beta", …) is the biggest offender.

The `object` dtype is a column of Python strings (or mixed types) — each element is a
heap-allocated object (a separate Python object somewhere in memory, reached by a pointer).
It is typically 5–10× more memory than the semantic data requires and 20–100× slower to
process.

```python
import pandas as pd
import numpy as np

N = 1_000_000
rng = np.random.default_rng(0)
df = pd.DataFrame({
    'category': rng.choice(['alpha', 'beta', 'gamma', 'delta'], N),  # object dtype
    'value':    rng.standard_normal(N).astype(np.float64),
})

print("object dtype:")
print(f"  memory: {df.memory_usage(deep=True)['category'] / 1e6:.1f} MB")

# Convert to category
df['category_cat'] = df['category'].astype('category')
print("category dtype:")
print(f"  memory: {df.memory_usage(deep=True)['category_cat'] / 1e6:.1f} MB")
print(f"  categories: {df['category_cat'].cat.categories.tolist()}")
```

```output
object dtype:
  memory: 12.7 MB
category dtype:
  memory: 1.0 MB
  categories: ['alpha', 'beta', 'delta', 'gamma']
```

A ~13× reduction here: 12.7 MB down to 1.0 MB. The `category` dtype stores only the unique
category codes as integers internally; the string labels appear once. GroupBy on a
`category` column is also faster.

The code comment says "object dtype", but in pandas 3 (this kernel) the column is actually
the new Arrow-backed `str` dtype, which packs the text into one buffer and is already far
leaner than `object`. Under pandas 2, the same column as real `object` dtype measures about
54 MB — there, `category` was a ~50× win. Either way, the category column is a 1-byte code
per row plus a 4-entry lookup table.

> **Picture it:** an `object` column writes the word "gamma" out in full on a separate
> card for every row. A `category` column writes the four words once on a legend and then
> stores just a number (0–3) per row — like a map key.

### When NOT to use category

If a column has more than ~1,000 unique values, the overhead of the category map
outweighs the savings. Rule of thumb: `nunique / len(df) < 0.01` → use category.

> **In plain words:** category pays off when values *repeat a lot*. If almost every row
> is different (user IDs, free text), the legend would be as long as the data itself.

## Downcasting numerics

**Downcasting** means switching a column to a smaller number type — 64-bit to 32-bit —
when the values fit. Half the bytes per number means half the memory.

If you're certain values fit in float32 or int32, downcast to halve memory:

```python
import pandas as pd
import numpy as np

rng = np.random.default_rng(0)
df = pd.DataFrame({
    'int_col':   rng.integers(0, 1000, 1_000_000),          # int64
    'float_col': rng.standard_normal(1_000_000),             # float64
})

before = df.memory_usage(deep=True)[1:].sum() / 1e6
df['int32']   = df['int_col'].astype(np.int32)
df['float32'] = df['float_col'].astype(np.float32)
after = df[['int32', 'float32']].memory_usage(deep=True)[1:].sum() / 1e6

print(f"Before: {before:.1f} MB  After: {after:.1f} MB  ratio: {before/after:.1f}×")
```

```output
Before: 16.0 MB  After: 8.0 MB  ratio: 2.0×
```

Exactly 2×: two columns of 1 million 8-byte numbers (16 MB) became two columns of 4-byte
numbers (8 MB). Integers 0–999 fit easily in int32 (which reaches about 2.1 billion).

Downcast when: integers are counts or codes (int16/int32 suffice), values are ML features
not requiring float64 precision. Don't downcast aggregated statistics or intermediate
computations — accumulate in float64, then downcast the final result.

> **Watch out:** `astype(np.int16)` on a value outside $-32768$ to $32767$ wraps around
> silently, as in ch. 1. Check `col.min()` and `col.max()` before you downcast integers.

## `.apply()` is a loop — never use it on large DataFrames

`.apply` with `axis=1` calls your Python function once for every row. That is the slow
Python loop from ch. 2 wearing a pandas costume.

`.apply(func, axis=1)` passes each row as a Series to `func`. Python function call per row.
For 1 million rows, that's 1 million Python-level function calls.

```python
import pandas as pd
import numpy as np
import time

rng = np.random.default_rng(0)
N = 500_000
df = pd.DataFrame({'a': rng.standard_normal(N), 'b': rng.standard_normal(N)})

# Slow: row-level apply
t0 = time.perf_counter()
slow = df.apply(lambda row: row['a'] ** 2 + row['b'] ** 2, axis=1)
apply_ms = (time.perf_counter() - t0) * 1000

# Fast: vectorized
t0 = time.perf_counter()
fast = df['a'] ** 2 + df['b'] ** 2
vec_ms = (time.perf_counter() - t0) * 1000

print(f"apply: {apply_ms:.0f} ms   vec: {vec_ms:.1f} ms   ratio: {apply_ms/vec_ms:.0f}×")
print("results equal:", np.allclose(slow.values, fast.values))
```

```output
apply: 2058 ms   vec: 3.1 ms   ratio: 662×
results equal: True
```

Same answer (`results equal: True`), but hundreds of times slower with `apply`. Each of the
500,000 rows was wrapped in a new Series object and passed through the Python interpreter;
the vectorized line did three whole-column operations in compiled code.

**Vectorized pandas/NumPy is ~500× faster than `.apply(axis=1)`.** If you think you need
`apply`, first ask: can I express this as arithmetic on columns, NumPy ufuncs, or a
groupby transform? The answer is almost always yes.

### When apply is unavoidable

Column-level `apply(func, axis=0)` is fine (one call per column, not per row).
Row-level apply is justified only for calls to external services or for complex logic
that truly cannot be vectorized (and then the bottleneck is likely the external call, not Python).

> **In plain words:** if/else per row → `np.where`; several cases → `np.select`; lookup
> per row → `map` or a merge; per-group maths → `groupby().transform`. Row-level `apply`
> is the last resort, not the first tool.

## `numexpr` — fast multi-threaded arithmetic

**numexpr** takes a formula written as a string, compiles it, and evaluates it in chunks
on several threads at once, without building the in-between arrays NumPy would create.

For large float64 arrays with multi-step arithmetic, `numexpr` compiles the expression
to native code and uses multiple threads:

```python
import pandas as pd
import numpy as np
import numexpr as ne
import time

N = 10_000_000
rng = np.random.default_rng(0)
a = rng.standard_normal(N)
b = rng.standard_normal(N)
c = rng.standard_normal(N)

# NumPy (single-threaded, materialized intermediates)
t0 = time.perf_counter()
result_np = a**2 + b**2 - 2*a*c
np_ms = (time.perf_counter() - t0) * 1000

# numexpr (multi-threaded, no intermediate arrays)
t0 = time.perf_counter()
result_ne = ne.evaluate('a**2 + b**2 - 2*a*c')
ne_ms = (time.perf_counter() - t0) * 1000

print(f"numpy:   {np_ms:.0f} ms")
print(f"numexpr: {ne_ms:.0f} ms  ratio: {np_ms/ne_ms:.1f}×")
print("equal:", np.allclose(result_np, result_ne))
```

```output
numpy:   1028 ms
numexpr: 61 ms  ratio: 16.8×
equal: True
```

Same result, many times faster. With 10 million elements, NumPy builds a temporary 80 MB
array for every step (`a**2`, `b**2`, their sum, `2*a`, `2*a*c`) and walks memory once per
step; numexpr walks it once, in cache-sized chunks, on every core.

`numexpr` also avoids creating intermediate arrays (`a**2`, `b**2` each allocate a new
array in NumPy; numexpr fuses them into one pass). pandas `.query()` uses numexpr
internally when the query is a pure arithmetic/comparison expression.

> **Picture it:** NumPy cooks a recipe one ingredient at a time, putting each half-done
> step in its own bowl. numexpr does all the steps to one spoonful at a time, with no extra
> bowls — and several cooks share the work.

## Reading memory with `info()`

`info()` is a one-screen health check: every column's type, how many values are missing,
and how much memory the whole table uses.

```python
import pandas as pd
import numpy as np

rng = np.random.default_rng(0)
df = pd.DataFrame({
    'id':       rng.integers(0, 1000, 10_000),
    'category': rng.choice(['X', 'Y', 'Z'], 10_000),
    'value':    rng.standard_normal(10_000),
    'flag':     rng.integers(0, 2, 10_000).astype(bool),
})

df.info(memory_usage='deep')
```

```output
<class 'pandas.DataFrame'>
RangeIndex: 10000 entries, 0 to 9999
Data columns (total 4 columns):
 #   Column    Non-Null Count  Dtype
---  ------    --------------  -----
 0   id        10000 non-null  int64
 1   category  10000 non-null  str
 2   value     10000 non-null  float64
 3   flag      10000 non-null  bool
dtypes: bool(1), float64(1), int64(1), str(1)
memory usage: 254.0 KB
```

The `Non-Null Count` column says no values are missing. The `Dtype` column is the important
one: `category` shows as `str` (pandas 3's text dtype), `flag` is `bool` (1 byte per row).
Only `memory_usage='deep'` measures the real size of text columns; without it pandas
reports just the pointers.

The `object` column (category) uses most memory despite having only 3 unique values.
Converting it to `category` drops total memory to ~395 KB. (With pandas 3's `str` dtype the
text column is about 90 KB of the 254 KB total; converting it to `category` brings the
total down to about 176 KB.)

## Recap in plain words

- Measure first: `info(memory_usage='deep')` for memory, `perf_counter`/`%timeit` for time.
- Repeated text → `category` (codes + a small lookup table).
- Downcast numbers that fit (int64 → int32/int16, float64 → float32) — but accumulate
  statistics in float64.
- Row-wise `.apply` is a Python loop; rewrite it as column arithmetic, `np.where`,
  `np.select`, `map`, or `transform`.
- `numexpr` fuses multi-step arithmetic into one multi-threaded pass.

## Try it Yourself

```python
import pandas as pd
import numpy as np
import time

rng = np.random.default_rng(42)
N = 2_000_000

df = pd.DataFrame({
    'region':  rng.choice(['BD', 'IN', 'PK', 'LK', 'NP'], N),   # object → category
    'segment': rng.integers(0, 50, N),                            # int64 → int16
    'score':   rng.standard_normal(N).astype(np.float64),
    'weight':  rng.uniform(0, 1, N).astype(np.float64),
})

print("Before optimization:")
print(f"  memory: {df.memory_usage(deep=True).sum() / 1e6:.1f} MB")

# 1) Optimize dtypes
df['region']  = df['region'].astype('category')
df['segment'] = df['segment'].astype(np.int16)
df['score']   = df['score'].astype(np.float32)
df['weight']  = df['weight'].astype(np.float32)

print("After optimization:")
print(f"  memory: {df.memory_usage(deep=True).sum() / 1e6:.1f} MB")

# 2) Time: groupby on object vs category
df_obj = df.copy()
df_obj['region'] = df_obj['region'].astype(str)   # back to object

t0 = time.perf_counter()
_ = df_obj.groupby('region')['score'].mean()
obj_ms = (time.perf_counter() - t0) * 1000

t0 = time.perf_counter()
_ = df.groupby('region')['score'].mean()
cat_ms = (time.perf_counter() - t0) * 1000

print(f"\ngroupby object: {obj_ms:.1f} ms   category: {cat_ms:.1f} ms   ratio: {obj_ms/cat_ms:.1f}×")
```

```output
Before optimization:
  memory: 68.0 MB
After optimization:
  memory: 22.0 MB

groupby object: 60.8 ms   category: 24.2 ms   ratio: 2.5×
```

Two wins in one run: memory fell to about a third, and grouping on the `category` column
was faster than on plain text, because pandas groups small integer codes instead of
comparing strings. Try leaving `score` and `weight` as float64 and see how much of the
saving was from downcasting versus from the category.

## Exercise

Take a DataFrame with 3 million rows: one `object` column (10 unique values), one float64,
one int64. Measure memory before and after dtype optimization (category + float32 + int32).
Then verify that `groupby('cat').mean()` gives identical results before and after.

> **Hint:** compute the reference groupby *before* converting anything, and compare with
> `np.allclose` and a small tolerance — float32 can't match float64 to the last digit.

<details>
<summary>Solution</summary>

```python
import pandas as pd
import numpy as np

rng = np.random.default_rng(0)
N = 3_000_000
df = pd.DataFrame({
    'cat':  rng.choice([f'c{i}' for i in range(10)], N),
    'val':  rng.standard_normal(N),
    'cnt':  rng.integers(0, 10000, N),
})

before_mb = df.memory_usage(deep=True).sum() / 1e6
ref = df.groupby('cat')['val'].mean()

# Optimize
df['cat'] = df['cat'].astype('category')
df['val'] = df['val'].astype(np.float32)
df['cnt'] = df['cnt'].astype(np.int32)

after_mb = df.memory_usage(deep=True).sum() / 1e6
opt = df.groupby('cat')['val'].mean()

print(f"Memory: {before_mb:.1f} MB → {after_mb:.1f} MB  ({before_mb/after_mb:.1f}×)")
print("Results close:", np.allclose(ref.values, opt.values, atol=1e-4))
# float32 has ~1e-7 relative error vs float64, so results may differ slightly
```

The optimized frame gives the same group means to about 4 decimal places — the expected
float32 rounding — while using a fraction of the memory. Category conversion changes how
the labels are stored, never which rows belong to which group.
</details>
