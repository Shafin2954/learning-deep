## The five-step loop

All of deep learning training is one small routine repeated many thousands of times: guess,
measure the error, work out who is to blame, adjust, repeat. This chapter writes that routine
down and then makes it fit on a small graphics card.

Everything so far — forward (F1–F2), loss (F3), optimizer (F4), normalization (F5),
regularization (F6) — comes together in the **training loop**. It's the same five
steps whether you're training a toy MLP or fine-tuning a Bengali LLM. This chapter
nails the loop and then confronts your real constraint: an **8GB RTX 3070 Ti**, which
is small for LLMs. The tricks that make a fine-tune *fit* live here.

The "8GB" is the GPU's own memory (**VRAM**). Weights, gradients, optimizer statistics and
activations must all fit in it at once, or the run crashes.

The loop, always the same five steps:

1. **Forward** — run a batch through the model to get predictions.
2. **Loss** — compare predictions to targets (cross-entropy, F3).
3. **Backward** — `loss.backward()` fills every parameter's `.grad` (F2's backprop).
4. **Step** — the optimizer updates weights (`optimizer.step()`, F4); then
   `optimizer.zero_grad()` to clear grads for the next batch.
5. **Repeat** over batches (one full pass = an *epoch*), tracking validation for
   early stopping (F6).

> **Picture it:** practising free throws. Shoot (forward), see how far you missed (loss),
> figure out what your arm did wrong (backward), adjust your form (step), and shoot again
> (repeat). Wiping the slate clean between shots is `zero_grad()`; skip it and you keep
> correcting for *every* past miss at once.

That's the entire engine of deep learning. Memorize the order; the most common bug
is forgetting `zero_grad()` (gradients accumulate across batches and the model goes
haywire) — which, ironically, is the same mechanism we *deliberately* exploit below.

PyTorch *adds* each new gradient into `.grad` rather than overwriting it. That design is what
makes gradient accumulation possible, and what makes a missing `zero_grad()` a silent bug.

**Batching.** You process data in mini-batches, not one example at a time (too slow,
noisy) or all at once (won't fit memory). Batch size trades memory for gradient
stability. On 8GB with an LLM, your batch size will be *small* — sometimes 1.

A **mini-batch** is a small group of examples, often 8 to 64, whose average gradient is used
for one update. Bigger batches give a steadier gradient estimate but need more memory.

## The four levers that make LLMs fit in 8GB

A 7-billion-parameter model stored in 32-bit floats needs 28 GB for the weights alone, before
gradients or optimizer state. Four tricks close that gap: smaller numbers, smaller batches added
up, recomputing instead of storing, and freezing most of the model.

### Mixed precision (fp16/bf16)

Store most numbers with 16 bits instead of 32, which halves their memory. Some precision is
lost, but neural networks barely notice.

Store activations/weights in 16-bit instead of 32-bit — roughly half the memory and
faster math, with negligible accuracy loss. Prefer **bf16** if your GPU supports it
(more stable than fp16). This is the single biggest free win.
(`torch.cuda.amp` / `Trainer(fp16=True/bf16=True)`.)

**fp16** and **bf16** are two 16-bit number formats. fp16 keeps more digits of precision but
overflows above about 65,504. bf16 keeps fewer digits but has the same range as 32-bit floats,
so it almost never overflows. That range is why bf16 is "more stable". "Mixed" precision means
the risky parts, such as the weight update, stay in 32 bits.

### Gradient accumulation

If a batch of 16 does not fit, run eight batches of 2, add up their gradients, and only then
take one step. The step is the same as if you had used a batch of 16.

Want an *effective* batch size of 16 but only 2 fit? Run 8 micro-batches, summing
their gradients, and `step()` once. You get the stability of batch-16 at the memory
of batch-2 — by *intentionally* not zeroing grads between micro-batches:

$$
\text{effective\_batch} = \text{micro\_batch} \times \text{accumulation\_steps}
$$

> **In plain words:** the batch the optimizer effectively sees is the size of each small batch
> times how many of them you add up before stepping: $2 \times 8 = 16$.

> **Watch out:** divide each micro-batch's loss by `accum_steps` (the loop below does). Without
> it, the summed gradient is 8 times too large, which acts like an 8-times-larger learning rate.

### Gradient checkpointing

The backward pass needs each layer's activations from the forward pass. Checkpointing throws
most of them away and recomputes them when they are needed, trading time for memory.

Don't store every layer's activations for the backward pass; recompute them on the
fly. Trades ~30% more compute for a large memory saving — often the difference
between OOM and training. (`model.gradient_checkpointing_enable()`.)

**OOM** stands for "out of memory", the crash you get when the GPU's memory is full.

> **Picture it:** hiking with a notebook. Instead of writing down every turn you took, you note
> only the major junctions. On the way back, when you need a detail between two junctions, you
> re-walk that short stretch. More walking, much less writing.

### Quantization (4-bit) + LoRA = QLoRA

Store the big frozen model in very coarse 4-bit numbers, and train only small add-on pieces at
normal precision.

Load the frozen base model in 4-bit (`bitsandbytes`) and train only small LoRA
adapters. This is *the* technique for fine-tuning a 7B model on 8GB. It gets its
own chapter (Bengali ch. 9); know here that it's a memory technique built on top of
this loop.

**Quantization** means storing numbers with fewer bits by rounding them onto a coarse grid. At 4
bits, a 7B model's weights take about 3.5 GB instead of 28 GB. **Frozen** weights are never
updated, so they need no gradients and no optimizer state.

Also cap **`max_length`**: every token costs memory quadratically in attention, and
Bengali's high fertility (Bengali ch. 3) inflates token counts — so choose
`max_length` from your *actual* length distribution (F15), don't default to 512
blindly.

"Quadratically" means doubling the length roughly quadruples attention's memory: every token
attends to every other token, so 512 tokens make $512^2 \approx 262{,}000$ attention scores per
head, and 1,024 tokens make about a million.

## A complete PyTorch fine-tuning loop

Here are the five steps and the memory tricks together, in the shape you will use for real. It
needs a GPU and a Hugging Face–style model whose output carries a `.loss`, so the block only
defines the function.

```python
# A real PyTorch fine-tuning loop (run locally on your GPU / Kaggle).
# Reads as the five steps; the 8GB tricks are the commented flags.
import torch
from torch.cuda.amp import autocast, GradScaler

def train(model, loader, val_loader, epochs=3, lr=2e-5,
          accum_steps=8, patience=2):
    opt = torch.optim.AdamW(model.parameters(), lr=lr, weight_decay=0.01)  # F4/F6
    scaler = GradScaler()                                  # mixed precision (fp16)
    model.gradient_checkpointing_enable()                 # memory: recompute acts
    best, bad, best_state = float("inf"), 0, None

    for epoch in range(epochs):
        model.train()
        opt.zero_grad()
        for i, batch in enumerate(loader):
            with autocast():                              # 16-bit forward
                out = model(**batch)                      # 1) forward
                loss = out.loss / accum_steps             # 2) loss (scaled for accum)
            scaler.scale(loss).backward()                 # 3) backward (accumulates)
            if (i + 1) % accum_steps == 0:                # step every accum_steps
                scaler.unscale_(opt)
                torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)  # anti-NaN
                scaler.step(opt); scaler.update()         # 4) step
                opt.zero_grad()

        val = evaluate(model, val_loader)                 # 5) track val (F6)
        if val < best - 1e-4:
            best, bad, best_state = val, 0, {k: v.cpu().clone()
                                            for k, v in model.state_dict().items()}
        else:
            bad += 1
            if bad >= patience:
                break                                     # early stopping
    if best_state:
        model.load_state_dict(best_state)                 # restore BEST, not last
    return model

print("train() defined; call it locally with your model and DataLoaders.")
```

```output
train() defined; call it locally with your model and DataLoaders.
```

The printed line only confirms that the function was defined without errors; running it needs
your model, data loaders and an `evaluate()` function that returns a validation loss. Find each
step in the code: the `autocast()` block is the forward pass and loss,
`scaler.scale(loss).backward()` is backward, the `if (i + 1) % accum_steps == 0` branch is the step, and the
validation check after each epoch drives early stopping with "restore best".

This is a RUN-LOCALLY block (requires `torch`). Run it on your GPU or Kaggle.

A few lines deserve a closer look:

- **`GradScaler`** multiplies the fp16 loss by a large factor before backward, so tiny
  gradients do not round to zero, and divides it back out (`unscale_`) before the update.
  With bf16 you do not need it.
- **`clip_grad_norm_(..., 1.0)`** is **gradient clipping**: if the combined length of all
  gradients exceeds 1.0, they are scaled down to length 1.0. One freak batch can then no longer
  launch the weights into `nan` territory.
- **`best_state`** stores copies on the CPU (`.cpu().clone()`), so the backup does not eat GPU
  memory.

> **Watch out:** in recent PyTorch versions, `torch.cuda.amp.autocast` and
> `torch.cuda.amp.GradScaler` are deprecated in favour of `torch.amp.autocast("cuda")` and
> `torch.amp.GradScaler("cuda")`. The old names still work but print a warning.

## Debugging a loop that won't train

When training misbehaves, the symptom usually points straight at the cause. Match the symptom,
then try the fixes in the order given.

A short, ordered checklist saves hours:

- **Loss is NaN/inf** — learning rate too high (lower it, add warmup, F4); fp16
  overflow (switch to bf16, or add gradient clipping `max_norm=1.0`); a bad batch
  (un-normalized text, F2 — check your data).
- **Loss doesn't move** — learning rate too low; forgot to unfreeze the right params;
  forgot `zero_grad()` placement; labels misaligned with inputs.
- **Train loss falls, val loss rises** — overfitting; apply F6 (early stop first).
- **CUDA out of memory** — smaller batch + more accumulation; enable mixed precision
  and gradient checkpointing; shorter `max_length`; QLoRA.
- **Overfits instantly / loss ~0 epoch 1** — label leakage (F15) or a trivial feature;
  be suspicious of "too good."

**Label leakage** means the answer has slipped into the inputs somewhere, so the model can read
it instead of learning it (F15).

> **Watch out:** a good first sanity check for any new loop is to train on a single batch of 8
> examples for a few hundred steps. A correct loop drives that loss close to 0. If it cannot
> even memorize 8 examples, the bug is in the loop, not in the data or the model size.

**Reproducibility.** Set all seeds, log your config, and save checkpoints. In a
competition you *will* need to reproduce a good run; an unseeded, unlogged run that
scored well but can't be rebuilt is worthless.

A **seed** is the starting value of a random-number generator. The same seed gives the same
sequence of "random" shuffles, dropout masks and initial weights, so the run can be repeated.

## Recap in plain words

- Every training run is the same five steps: forward, loss, backward, step, repeat.
- PyTorch adds gradients into `.grad`, so you must zero them after each step, unless you are
  accumulating on purpose.
- Mixed precision halves memory by storing numbers in 16 bits; bf16 is the safer format.
- Gradient accumulation adds up several small batches before one step, to mimic a big batch.
- Gradient checkpointing recomputes activations during backward instead of storing them.
- QLoRA stores the frozen model in 4 bits and trains only small adapters.
- Match the symptom (NaN, flat loss, overfitting, OOM, too good) to its usual cause before
  changing anything.

## Try it Yourself

This is the same loop in plain NumPy, runnable on any CPU: XOR data, a 300/100 train/validation
split, mini-batches of 32, and early stopping with a patience of 3 epochs.

```python
# The loop's logic, runnable on CPU with the from-scratch MLP from F2.
import numpy as np
np.random.seed(0)
def softmax(z): z=z-z.max(-1,keepdims=True); e=np.exp(z); return e/e.sum(-1,keepdims=True)
def ce(z,y): return -np.log(softmax(z)[np.arange(len(y)),y]).mean()
relu=lambda x: np.maximum(0,x)

X=np.random.randn(400,2); y=(X[:,0]*X[:,1]>0).astype(int)
tr,va = slice(0,300), slice(300,400)                       # train / val split
W1=np.random.randn(2,16)*0.5; b1=np.zeros(16); W2=np.random.randn(16,2)*0.5; b2=np.zeros(2)

def fwd(Xb): h=relu(Xb@W1+b1); return h@W2+b2, h
best=1e9; bad=0; lr=0.3; batch=32
for epoch in range(40):
    idx=np.random.permutation(300)
    for s in range(0,300,batch):                           # mini-batches
        b=idx[s:s+batch]; Xb,yb=X[tr][b],y[tr][b]
        z,h=fwd(Xb); N=len(yb)
        dz=softmax(z); dz[np.arange(N),yb]-=1; dz/=N        # backward
        dW2=h.T@dz; db2=dz.sum(0); dh=dz@W2.T; dh[h<=0]=0
        dW1=Xb.T@dh; db1=dh.sum(0)
        for p,g in [(W1,dW1),(b1,db1),(W2,dW2),(b2,db2)]: p-=lr*g  # step
    vloss=ce(fwd(X[va])[0], y[va])                          # val (early stopping)
    if vloss<best-1e-4: best=vloss; bad=0
    else:
        bad+=1
        if bad>=3: print(f"early stop @ epoch {epoch}, best val {best:.3f}"); break
```

```output
early stop @ epoch 26, best val 0.129
```

The run trained for 26 epochs, then stopped because the validation loss had not improved for 3
epochs in a row. The best validation loss it reached was 0.129. That is a cross-entropy, so the
model gave the true class about $e^{-0.129} \approx 0.88$ probability on a typical validation
point, far from the $\ln 2 \approx 0.693$ of a coin flip.

Try a variation: set `batch=300` (one batch per epoch, full-batch training) and watch how many
more epochs it needs, or set `lr=3.0` and see what an oversized learning rate does to the
validation loss.

> **Hint:** `torch.optim.lr_scheduler.LambdaLR` multiplies the base learning rate by any
> function of the step count you give it. Call `sched.step()` right after `scaler.step(opt)`,
> inside the `accum_steps` branch, not once per micro-batch.

```python
import math, torch

def warmup_cosine(warmup, total):
    def factor(step):                                   # multiplier on the base lr
        if step < warmup:
            return step / warmup
        p = (step - warmup) / max(1, total - warmup)
        return 0.5 * (1 + math.cos(math.pi * min(p, 1.0)))
    return factor

# Inside train(): build it right after the optimizer.
# total = optimizer updates, not batches: len(loader) // accum_steps * epochs
model = torch.nn.Linear(4, 2)                           # stand-in model for a CPU check
opt = torch.optim.AdamW(model.parameters(), lr=2e-5, weight_decay=0.01)
sched = torch.optim.lr_scheduler.LambdaLR(opt, warmup_cosine(warmup=10, total=100))
for update in range(100):
    loss = model(torch.randn(8, 4)).pow(2).mean()
    loss.backward(); opt.step(); opt.zero_grad()
    sched.step()                                        # once per optimizer update
    if update in (0, 9, 50, 99):
        print(f"update {update:3d}: lr {sched.get_last_lr()[0]:.2e}  loss {loss.item():.3f}")
```

On this stand-in model the learning rate logs as $2.00 \times 10^{-6}$ after the first update,
reaches the peak $2.00 \times 10^{-5}$ at update 9, is $1.14 \times 10^{-5}$ at update 50, and is
0 at the end. (The loss values here are meaningless; the targets are random noise.) In the real
`train()`, put `sched.step()` next to `scaler.step(opt)` and log `sched.get_last_lr()[0]` and
`loss.item() * accum_steps` there. The `min(p, 1.0)` stops the rate from climbing back up if
training runs past `total`. The OOM and NaN answers are in the problem statement: both lists
start with the cheapest change that targets the cause.
