## What a pretrained model actually gives you

A downloaded model is two parts: a big "body" that has already learned the language, and a
small "head" on top that turns the body's output into an answer for one specific job.
Fine-tuning is teaching that pair your job without wiping what the body already knows.

A **checkpoint** — the saved files of a trained model — is: the token embedding table (F8), a
stack of $N$ transformer blocks (F12) with their trained $Q/K/V/W_o$ and MLP weights, the
positional scheme (F11, often **RoPE**, rotary position embeddings, which encode word order by
rotating vectors), a final norm, and a **head**. The "body" (embeddings + blocks) holds the
general language knowledge learned in **pretraining** (the long first training run on raw
text). The **head** is the task-specific output layer (ch. 7). Fine-tuning mostly means:
keep the body's knowledge, adapt it to your task.

> **Picture it:** the body is a fluent Bengali speaker; the head is the form they fill in. Change
> the form from "positive/negative" to "person/place/organization" and the same speaker can do
> the new job after a short briefing. You rarely need to re-teach them the language.

## Reading the config: the numbers that matter

Every Hugging Face model ships a small `config.json` that lists its size. A handful of those
numbers tell you how much memory it needs and how much Bengali text it can read at once.

- `hidden_size` ($d$) — vector width per token. Bigger = more capacity + more memory.
- `num_hidden_layers` ($N$) — how many blocks. Depth.
- `num_attention_heads` ($h$) — heads per block (F10).
- `intermediate_size` — the MLP's hidden width (usually $4d$, F12).
- `vocab_size` — drives the embedding table and the output head.
- `max_position_embeddings` — the context limit. Bengali fertility (ch. 3) means fewer *words*
  fit than this number suggests; plan `max_length` accordingly.
- `rope_theta` / position config — the positional scheme; the knob for context extension (F11).

These tell you memory cost and where your inputs will truncate — both decisive on 8 GB.

## Inspecting a model config (RUN-LOCALLY)

The plain idea: load only the config first (a tiny file), print the size numbers, then load the
full model once to count its parameters.

```python
# Inspect a model the way a fine-tuner should: read the config, find the knobs.
from transformers import AutoConfig, AutoModel

cfg = AutoConfig.from_pretrained("csebuetnlp/banglabert")
for k in ["hidden_size", "num_hidden_layers", "num_attention_heads",
          "intermediate_size", "vocab_size", "max_position_embeddings"]:
    print(f"{k:26s}: {getattr(cfg, k, 'n/a')}")

# Count parameters and see how few a head adds vs the body.
model = AutoModel.from_pretrained("csebuetnlp/banglabert")
total = sum(p.numel() for p in model.parameters())
print(f"\nbody parameters: {total/1e6:.1f}M")
# A classification head is hidden_size x num_labels — kilobytes next to this. That
# asymmetry is exactly why head-only / LoRA training is cheap.
```

```output
hidden_size               : 768
num_hidden_layers         : 12
num_attention_heads       : 12
intermediate_size         : 3072
vocab_size                : 32000
max_position_embeddings   : 512

body parameters: 110.0M
```

Read it top to bottom. `hidden_size` 768 and `intermediate_size` 3072 confirm the usual $4d$
rule ($4 \times 768 = 3072$). `max_position_embeddings` is 512, so at a fertility near 2.5 you
fit roughly 205 Bengali words per input. The last line, 110.0M parameters, is the body. A
3-class head on top is $768 \times 3$ weights plus 3 biases, about 2.3 thousand numbers, a
fraction of a percent of the body.

> **Watch out:** `AutoModel` loads the body only. When you load `AutoModelForSequenceClassification`
> instead, Hugging Face warns that some weights are "newly initialized". That warning is expected:
> it is the fresh, random head you are about to train.

## Three fine-tuning strategies

You can change everything, almost nothing, or a tiny add-on. Each step down the list trades a
little capacity for a lot less memory and less risk of memorizing a small dataset.

The less you change, the less you can overfit, and the less memory you need. On a
modest-resource language with a small GPU, that pushes you *down* the list.

### 1. Full fine-tuning

Update *all* weights. Most capacity, most memory, most **overfitting** (learning the training
examples by heart instead of the pattern) risk on small Bengali data (F6). Feasible on 8 GB only
for small encoders (BanglaBERT). Needs the smallest learning rate ($\approx 2 \times 10^{-5}$)
and **warmup** (starting the learning rate near zero and raising it over the first steps) (F4).

### 2. Head-only / feature-based

Freeze the body, train only a new head (or train a classifier on frozen embeddings, ch. 5).
Cheapest, least overfitting, surprisingly strong on tiny data. Your baseline.

### 3. Parameter-efficient (LoRA/QLoRA)

Freeze the body, inject tiny trainable **adapter** matrices — small extra weights added beside
the frozen ones — into the attention/MLP layers. Only ${\sim}0.1$–$1\%$ of the parameters move,
so it's memory-light *and* a built-in regularizer (F6). This is how you fine-tune a 1B–8B model on
8 GB. Full chapter next (ch. 8–9).

> **Picture it:** full fine-tuning is renovating the whole house. Head-only is buying new
> furniture. LoRA is adding a few clip-on shelves: cheap, reversible, and the walls stay as built.

## Freezing and learning-rate layering

The plain idea: the bottom layers know general things about language and should barely move;
the top layers and the head are closer to your task and can move more.

- **Freeze lower layers, train upper ones** — lower transformer layers encode general features,
  upper layers are more task-specific.
- **Discriminative learning rates** — smaller $\eta$ for early layers, larger for the head (the
  head starts random and needs to move more). Optional but helps on small data.

> **Watch out:** using the head's learning rate (for example $10^{-3}$) on the whole body can
> erase pretrained knowledge in a few hundred steps, a failure called catastrophic forgetting.
> If your validation score collapses early, check the body's learning rate first.

## Recap in plain words

- A checkpoint is a pretrained body (embeddings plus transformer blocks) and a small task head.
- The config tells you width, depth, vocabulary, and the context limit; BanglaBERT has 768 width, 12 layers, and 512 positions.
- BanglaBERT's body is 110.0M parameters, while a 3-class head is about 2.3 thousand.
- Full fine-tuning changes every weight, head-only changes only the head, and LoRA trains small adapters beside frozen weights.
- Small data or a small GPU pushes you toward head-only or LoRA.
- Lower layers deserve smaller learning rates than upper layers and the head.

## Try it Yourself

This calculator turns the chapter's rules of thumb into code: one answer for "does full
fine-tuning fit?" and one for "how much should I regularize given my data size?".

```python
# Decide your strategy from model size and data size — a rule-of-thumb calculator.
def strategy(params_millions, train_examples, vram_gb=8):
    if params_millions <= 300 and vram_gb >= 8:
        full = "full fine-tune feasible"
    else:
        full = "full fine-tune NOT feasible on this VRAM"
    if train_examples < 2000:
        reg = "tiny data -> prefer head-only or LoRA (less overfit, F6)"
    elif train_examples < 20000:
        reg = "moderate data -> LoRA/QLoRA is the sweet spot"
    else:
        reg = "lots of data -> full FT (if it fits) or LoRA both fine"
    return full, reg

for p, n in [(110, 1500), (1000, 5000), (7000, 800)]:
    f, r = strategy(p, n)
    print(f"{p:>5}M params, {n:>5} examples -> {f}; {r}")
# Notice: big model + tiny data -> QLoRA, not full FT. The math pushes you down
# the strategy list every time data is small or the GPU is small.
```

```output
  110M params,  1500 examples -> full fine-tune feasible; tiny data -> prefer head-only or LoRA (less overfit, F6)
 1000M params,  5000 examples -> full fine-tune NOT feasible on this VRAM; moderate data -> LoRA/QLoRA is the sweet spot
 7000M params,   800 examples -> full fine-tune NOT feasible on this VRAM; tiny data -> prefer head-only or LoRA (less overfit, F6)
```

Row 1 (BanglaBERT-sized, 1500 examples) fits for full fine-tuning, but the tiny-data rule still
recommends head-only or LoRA. Rows 2 and 3 (1000M and 7000M) fail the 300M memory rule, so
only adapters are left. Row 3 is the classic trap: the biggest model with the least data.

Variation to try: call `strategy(110, 50000)` and `strategy(1000, 5000, vram_gb=24)`. The second
still says "NOT feasible", because the function only checks the 300M size rule; extend it so more
VRAM raises the limit.
