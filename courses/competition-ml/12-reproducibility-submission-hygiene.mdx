## The two ways competitions are lost after the modelling is done

Good models still lose competitions in the last mile: you trust a gain that was luck, or you
upload a file with the answers in the wrong rows. Both are bookkeeping problems with bookkeeping
fixes.

The first is believing a gain that was seed noise. The second is uploading a file whose rows are
in the wrong order. Neither has anything to do with machine learning, and both are entirely
preventable with about forty lines of code.

A **seed** is the starting number for a random number generator. Same seed, same "random" choices;
different seed, different ones. **Reproducible** means running the same code again gives the same
numbers.

> **Picture it:** a pilot's pre-flight checklist. Nobody thinks the pilot cannot fly; the checklist
> exists because skilled people still forget the fuel cap. This chapter is that checklist for the
> moment you press "submit".

The setup: 8,000 training rows and a 3,000-row test set with ids from 100,000 to 102,999.

```python
import numpy as np
import pandas as pd
import hashlib, json
from sklearn.datasets import make_classification
from sklearn.model_selection import StratifiedKFold

                           class_sep=0.7, flip_y=0.03, random_state=0)
X = pd.DataFrame(X, columns=[f"f{i}" for i in range(X.shape[1])])
test_ids = np.arange(100_000, 103_000)
X_test = pd.DataFrame(np.random.default_rng(1).normal(0, 1, (3_000, 20)),
                      columns=X.columns)
print(f"train {X.shape} | test {X_test.shape}")
```

## How much of your "improvement" is the seed?

Run the same model with a different seed and the score moves a little. If your "improvement" is
smaller than that wobble, it is not an improvement. Measure the wobble first.

There are two seeds to vary: the **model seed** (which trees a forest grows) and the **fold seed**
(which rows land in which CV fold). The experiment uses 1,200 rows, so each of the 4 folds
validates on only 300.

```python
# a realistic competition size: noise is invisible on 8,000 easy rows
X_small, y_small = X.iloc[:1_200], y[:1_200]

def cv_auc(make_model, X, y, cv_seed=0, k=4):
    cv = StratifiedKFold(n_splits=k, shuffle=True, random_state=cv_seed)
    scores = []
    for tr, va in cv.split(X, y):
        m = make_model().fit(X.iloc[tr], y[tr])
        scores.append(roc_auc_score(y[va], m.predict_proba(X.iloc[va])[:, 1]))
    return float(np.mean(scores))

model_seeds = [cv_auc(lambda s=s: RandomForestClassifier(n_estimators=120, min_samples_leaf=5,
                                                         random_state=s, n_jobs=1),
                      X_small, y_small)
               for s in range(6)]
cv_seeds = [cv_auc(lambda: RandomForestClassifier(n_estimators=120, min_samples_leaf=5,
                                                  random_state=0, n_jobs=1),
                   X_small, y_small, cv_seed=s)
            for s in range(6)]
print(f"varying the MODEL seed (folds fixed): mean {np.mean(model_seeds):.4f} | "
      f"range {max(model_seeds) - min(model_seeds):.4f}")
print(f"  {[round(v, 4) for v in model_seeds]}")
print(f"varying the FOLD seed (model fixed) : mean {np.mean(cv_seeds):.4f} | "
      f"range {max(cv_seeds) - min(cv_seeds):.4f}")
print(f"  {[round(v, 4) for v in cv_seeds]}")
```

```output
varying the MODEL seed (folds fixed): mean 0.9505 | range 0.0011
  [0.9499, 0.9503, 0.951, 0.95, 0.9508, 0.9509]
varying the FOLD seed (model fixed) : mean 0.9517 | range 0.0047
  [0.9499, 0.9522, 0.9546, 0.9528, 0.95, 0.9506]
```

Changing only the model seed moves the CV score within a range of 0.0011 (0.9499 to 0.9510).
Changing only the fold seed moves it within 0.0047 (0.9499 to 0.9546).

Two different noise sources, and they are **not** the same size: the fold seed moves the score four
times as much as the model seed. That ordering is typical and it has a cause — changing the model
seed re-randomises 120 trees whose average is stable, while changing the fold seed changes *which
rows are being scored*, and 300 validation rows are a small sample.

Before you believe any improvement, compare it against both ranges, and against the larger one in
particular: a change under 0.005 on this data is not a change at all (eval-tuning ch. 12).

> **Watch out:** comparing model A on fold seed 0 with model B on fold seed 1 mixes the fold noise
> into the comparison. Always compare candidates on the *same* folds.

### Seed averaging is a technique; seed hunting is not

Training the same model with several seeds and averaging the predictions is honest: it removes
wobble. Trying many seeds and keeping the luckiest is dishonest to yourself: it keeps wobble.

```python
def oof_predictions(seed, k=4, cv_seed=0):
    cv = StratifiedKFold(n_splits=k, shuffle=True, random_state=cv_seed)
    oof = np.zeros(len(y))
    for tr, va in cv.split(X, y):
        m = RandomForestClassifier(n_estimators=120, min_samples_leaf=5,
                                   random_state=seed, n_jobs=1).fit(X.iloc[tr], y[tr])
        oof[va] = m.predict_proba(X.iloc[va])[:, 1]
    return oof

singles = [oof_predictions(s) for s in range(5)]
print(f"{'seeds averaged':>16} {'AUC':>8}")
for k_seeds in (1, 2, 3, 5):
    avg = np.mean(singles[:k_seeds], axis=0)
    print(f"{k_seeds:>16} {roc_auc_score(y, avg):>8.4f}")
best_seed = max(range(5), key=lambda i: roc_auc_score(y, singles[i]))
print(f"\nbest individual seed ({best_seed}): "
      f"{roc_auc_score(y, singles[best_seed]):.4f}  <- do NOT submit this one")
```

```output
  seeds averaged      AUC
               1   0.9733
               2   0.9739
               3   0.9740
               5   0.9741

best individual seed (1): 0.9740  <- do NOT submit this one
```

One seed scores 0.9733 out-of-fold; the average of five seeds scores 0.9741. The single best seed
(seed 1, 0.9740) sits right next to the five-seed average.

Averaging over seeds reduces variance and is a legitimate free gain — small here (+0.0008 from one
seed to five) because a 120-tree forest is already an average, and much larger for models that are
not, such as a single neural net or a boosted tree with aggressive subsampling.

*Choosing* the best seed is the opposite: maximising a noisy quantity, the same selection bias as
ch. 8's weight fitting in its purest form. Note that the best individual seed (0.9740) does not
even beat the five-seed average (0.9741) in-sample, and on the test set it has no reason to lead
at all. If you find yourself with a "best seed", you have found noise.

> **Picture it:** flipping five coins and keeping the one that landed heads does not give you a
> coin that lands heads more often. The "best seed" is that coin.

## Everything else that makes a run irreproducible

Fixing `random_state` is not the whole story. Thread counts, row order, library versions and
hashing can all change a result while the seed stays the same.

The code seeds the three random sources a NumPy and scikit-learn stack uses, then runs two tests:
the same forest on 1 versus 4 threads, and the same forest on shuffled rows.

```python
def set_all_seeds(seed=0):
    """The three that matter for a scikit-learn/numpy stack."""
    import random
    random.seed(seed)
    np.random.seed(seed)                 # legacy global RNG, still used by some libraries
    return np.random.default_rng(seed)   # the one you should actually pass around

rng = set_all_seeds(0)
print("seeded: python random, numpy legacy global, and a returned Generator")

a = RandomForestClassifier(n_estimators=60, random_state=0, n_jobs=1).fit(X, y)
b = RandomForestClassifier(n_estimators=60, random_state=0, n_jobs=4).fit(X, y)
print(f"same seed, 1 thread vs 4 threads, identical predictions: "
      f"{np.array_equal(a.predict_proba(X)[:, 1], b.predict_proba(X)[:, 1])}")

shuffled = np.random.default_rng(7).permutation(len(y))
c = RandomForestClassifier(n_estimators=60, random_state=0, n_jobs=1).fit(
    X.iloc[shuffled], y[shuffled])
same = np.array_equal(a.predict_proba(X)[:, 1], c.predict_proba(X)[:, 1])
print(f"same seed, rows shuffled before fitting, identical predictions: {same}")
```

```output
seeded: python random, numpy legacy global, and a returned Generator
same seed, 1 thread vs 4 threads, identical predictions: True
same seed, rows shuffled before fitting, identical predictions: False
```

Threads did not matter here (`True`): scikit-learn's forest assigns each tree its own seed, so the
trees come out the same however they are split across threads. Shuffling the rows did matter
(`False`).

Row order changes the result even with the seed fixed, because the RNG stream is consumed against
whatever order the data arrives in. That is the mechanism behind most "it worked yesterday"
reports. The checklist:

| Source | Fix |
|---|---|
| model RNG | `random_state=` on every estimator, written in the config |
| fold assignment | one splitter, one seed, created once and reused |
| row order | sort by a stable key before fitting, or record the order |
| library versions | pin them, and record them in the run manifest |
| `PYTHONHASHSEED` | set it if any code iterates over a `set` of strings |
| thread count | fix it if you need bit-identical output; expect tiny drift otherwise |
| GPU kernels | deterministic mode where the framework offers one, at a speed cost |

The less familiar rows, in plain words: **`PYTHONHASHSEED`** controls how Python orders the items
of a `set` of strings, which changes between runs unless you fix it. To **pin** a library version
means to write down the exact version (for example `pandas==3.0.6`) and install exactly that.

> **Watch out:** a `pd.concat` or `merge` can silently change row order. If a run differs from
> yesterday's with the same seed, check the row order before anything else.

## Building the submission

The model is done; now you must write its predictions into the organiser's file format. Every
prediction must land next to the id it belongs to.

The modelling is over. Everything from here is data handling, and it is where files get ruined.

The **sample submission** is the organiser's template file: the ids in the order they expect, and
a placeholder target. Here its ids are shuffled, as they often are in real competitions.

```python
model = HistGradientBoostingClassifier(max_depth=5, random_state=0).fit(X, y)
preds = model.predict_proba(X_test)[:, 1]

sample_submission = pd.DataFrame({"id": np.random.default_rng(3).permutation(test_ids),
                                  "target": 0.5})
sub_wrong = sample_submission.copy()
sub_wrong["target"] = preds                                  # concatenated by POSITION

right = pd.DataFrame({"id": test_ids, "target": preds})
sub_right = sample_submission[["id"]].merge(right, on="id", how="left")  # aligned by KEY

print(f"sample submission id order matches test order: "
      f"{np.array_equal(sample_submission['id'].values, test_ids)}")
print(f"correlation between the two submissions: "
      f"{np.corrcoef(sub_wrong.sort_values('id')['target'], sub_right.sort_values('id')['target'])[0, 1]:.4f}")
```

```output
sample submission id order matches test order: False
correlation between the two submissions: 0.0167
```

The sample's id order does not match the test order (`False`). The positional file and the
key-aligned file correlate at only 0.0167 — the positional file is essentially random.

Both files have the right ids, the right number of rows, and a plausible distribution of values.
One of them is a random permutation of the correct answer. **Always merge on the key; never assign
a column by position.**

> **Picture it:** handing back exam papers in the order you marked them, instead of reading the
> name on each. Every student gets a real grade — someone else's.

## A submission validator

Before uploading, run a function that checks everything that can go wrong with the file itself:
columns, row count, duplicates, missing ids, order, NaNs, range — and similarity to your last good
file.

```python
def validate_submission(sub, sample, id_col="id", target_col="target",
                        lo=0.0, hi=1.0, previous=None):
    problems, notes = [], []
    if list(sub.columns) != list(sample.columns):
        problems.append(f"columns {list(sub.columns)} != expected {list(sample.columns)}")
    if len(sub) != len(sample):
        problems.append(f"{len(sub)} rows, expected {len(sample)}")
    if sub[id_col].duplicated().any():
        problems.append(f"{int(sub[id_col].duplicated().sum())} duplicate ids")
    missing = set(sample[id_col]) - set(sub[id_col])
    if missing:
        problems.append(f"{len(missing)} ids missing")
    if not np.array_equal(sub[id_col].values, sample[id_col].values):
        problems.append("id order differs from the sample submission")
    t = sub[target_col]
    if t.isna().any():
        problems.append(f"{int(t.isna().sum())} NaN predictions")
    if t.min() < lo or t.max() > hi:
        problems.append(f"values outside [{lo}, {hi}]: min {t.min():.4f} max {t.max():.4f}")
    if t.nunique() < 10:
        problems.append(f"only {t.nunique()} distinct values")
    notes.append(f"mean {t.mean():.4f} | sd {t.std():.4f} | "
                 f"min {t.min():.4f} | max {t.max():.4f}")
    if previous is not None:
        joined = sub.merge(previous, on=id_col, suffixes=("", "_prev"))
        r = float(np.corrcoef(joined[target_col], joined[f"{target_col}_prev"])[0, 1])
        notes.append(f"correlation with previous submission: {r:.4f}")
        if r < 0.5:
            problems.append(f"correlation with the previous submission is only {r:.4f}")
    for n in notes:
        print(f"  note: {n}")
    for p in problems:
        print(f"  PROBLEM: {p}")
    print(f"  => {'OK' if not problems else str(len(problems)) + ' problem(s)'}")
    return not problems

print("correct submission:")
validate_submission(sub_right, sample_submission)
print("\npositionally-assigned submission:")
_ = validate_submission(sub_wrong, sample_submission, previous=sub_right)
```

```output
correct submission:
  note: mean 0.5313 | sd 0.3542 | min 0.0030 | max 0.9916
  => OK

positionally-assigned submission:
  note: mean 0.5313 | sd 0.3542 | min 0.0030 | max 0.9916
  note: correlation with previous submission: 0.0167
  PROBLEM: correlation with the previous submission is only 0.0167
  => 1 problem(s)
```

The correct file passes (`=> OK`). The positional file has the same mean, spread, minimum and
maximum to four decimals, so every value check passes. Only the last check fires: its
correlation with the known-good file is 0.0167.

The positional file passes every structural check — the only thing that catches it is the
correlation against a known-good submission. That is why the last check exists, and why you keep
your previous best on disk.

Now a file broken in five ways at once — NaNs, out-of-range values, an extra duplicated row:

```python
broken = sub_right.copy()
broken.loc[broken.index[:5], "target"] = np.nan
broken.loc[broken.index[5:10], "target"] = 1.7
broken = pd.concat([broken, broken.iloc[[0]]], ignore_index=True)
print("deliberately broken submission:")
_ = validate_submission(broken, sample_submission)
```

```output
deliberately broken submission:
  note: mean 0.5334 | sd 0.3570 | min 0.0030 | max 1.7000
  PROBLEM: 3001 rows, expected 3000
  PROBLEM: 1 duplicate ids
  PROBLEM: id order differs from the sample submission
  PROBLEM: 6 NaN predictions
  PROBLEM: values outside [0.0, 1.0]: min 0.0030 max 1.7000
```

All five problems are reported in one pass: 3,001 rows, 1 duplicate id, wrong order (the extra
row shifts everything after it), 6 NaNs (the 5 planted plus the duplicated first row), and a
maximum of 1.7000.

> **Watch out:** the validator *reports*; it does not stop you. Make your upload script refuse to
> continue when it returns `False` — that is the exercise below.

## Recap in plain words

- On 1,200 rows, the fold seed moved the score 0.0047 and the model seed 0.0011; smaller "gains"
  are noise.
- Averaging several seeds is a real, small gain; keeping the best seed is self-deception.
- Row order changes results even with a fixed seed; sort by a stable key.
- Always merge predictions onto the sample submission by id, never by position.
- Validate every file before upload, including a correlation check against your previous best.

## Try it Yourself

`submission_manifest` writes a small record of what a file is: model, config, CV score, seeds,
library versions, and a short **hash** — a fingerprint computed from the prediction values.

```python
def submission_manifest(sub, model_name, config, cv_score, seeds, target_col="target"):
    payload = sub[target_col].round(8).to_numpy().tobytes()
    return {
        "model": model_name,
        "config": config,
        "cv_score": round(float(cv_score), 6),
        "seeds": seeds,
        "n_rows": int(len(sub)),
        "pred_hash": hashlib.sha256(payload).hexdigest()[:12],
        "pred_mean": round(float(sub[target_col].mean()), 6),
        "libs": {"numpy": np.__version__, "pandas": pd.__version__},
    }

m1 = submission_manifest(sub_right, "hgb-depth5", {"max_depth": 5}, 0.8123,
                         {"model": 0, "cv": 0})
print(json.dumps(m1, indent=1))
resubmitted = sub_right.copy()
print(f"\nre-built file has the same hash: "
      f"{submission_manifest(resubmitted, 'hgb-depth5', {'max_depth': 5}, 0.8123, {'model': 0, 'cv': 0})['pred_hash'] == m1['pred_hash']}")
```

```output
{
 "model": "hgb-depth5",
 "config": {
  "max_depth": 5
 },
 "cv_score": 0.8123,
 "seeds": {
  "model": 0,
  "cv": 0
 },
 "n_rows": 3000,
 "pred_hash": "e4b74cdf5114",
 "pred_mean": 0.531283,

  "numpy": "2.5.2",
  "pandas": "3.0.6"
 }
}

```

The 12-character `pred_hash` is `e4b74cdf5114`. Rebuilding the same file gives the same hash
(`True`); change one prediction in the eighth decimal and the hash changes completely.

The prediction hash is the cheapest anti-mistake device in a competition: two submissions with the
same hash are the same file, whatever you named them, and a "new" model whose hash matches
yesterday's means you submitted the wrong thing. Add fields you find yourself wanting — the git
commit, the feature-set name, the blend weights (ch. 8).

Variation to try: build the manifest for `sub_wrong` and compare its hash and `pred_mean` with
`m1`. The means match exactly; only the hash tells the two files apart.

## Exercise

Build the last mile: a function that takes a set of candidate submissions with their CV scores,
picks the final two (one best, one diverse hedge), validates both, writes their manifests, and
refuses to proceed if anything fails. Test it on a set that includes one deliberately broken file.

> **Hint:** validate *first*, then choose among the files that passed. For the hedge, take the
> candidate least correlated with the champion among those whose CV is within a small tolerance of
> the champion's.

```python
rng = np.random.default_rng(11)
base = sub_right["target"].values
candidates = {
    "hgb":        {"pred": base, "cv": 0.8123, "seeds": {"model": 0, "cv": 0}},
    "hgb-seedavg": {"pred": np.clip(base + rng.normal(0, 0.01, len(base)), 0, 1),
                    "cv": 0.8141, "seeds": {"model": "0-4 averaged", "cv": 0}},
    "forest":     {"pred": np.clip(base * 0.7 + rng.random(len(base)) * 0.3, 0, 1),
                   "cv": 0.8065, "seeds": {"model": 0, "cv": 0}},
    "blend":      {"pred": np.clip(0.6 * base + 0.4 * rng.random(len(base)), 0, 1),
                   "cv": 0.8150, "seeds": {"model": "blend", "cv": 0}},
    "broken":     {"pred": np.where(rng.random(len(base)) < 0.02, np.nan, base),
                   "cv": 0.8200, "seeds": {"model": 9, "cv": 0}},
}

def final_two(candidates, sample, id_col="id", target_col="target"):
    frames, valid = {}, {}
    print("validation")
    for name, c in candidates.items():
        frame = sample[[id_col]].merge(
            pd.DataFrame({id_col: test_ids, target_col: c["pred"]}), on=id_col, how="left")
        print(f"  [{name}]")
        ok = validate_submission(frame, sample)
        frames[name], valid[name] = frame, ok

    usable = {n: candidates[n] for n in candidates if valid[n]}
    print(f"\nusable candidates: {sorted(usable)}")
    if not usable:
        raise RuntimeError("no valid submission")

    champion = max(usable, key=lambda n: usable[n]["cv"])
    corr = {}
    for name in usable:
        if name == champion:
            continue
        corr[name] = float(np.corrcoef(frames[champion][target_col],
                                       frames[name][target_col])[0, 1])
    # the hedge: the best-scoring candidate that is least correlated with the champion
    scored = sorted(corr.items(), key=lambda kv: kv[1])
    hedge = None
    for name, r in scored:
        if usable[name]["cv"] >= usable[champion]["cv"] - 0.01:
            hedge = (name, r)
            break
    hedge = hedge or (scored[0][0], scored[0][1])

    print(f"\nchampion: {champion} (CV {usable[champion]['cv']:.4f})")
    print(f"hedge   : {hedge[0]} (CV {usable[hedge[0]]['cv']:.4f}, "
          f"correlation with champion {hedge[1]:.4f})")
    print("\ncorrelation of each usable candidate with the champion:")
    for name, r in sorted(corr.items(), key=lambda kv: -kv[1]):
        print(f"  {name:12} {r:+.4f}  CV {usable[name]['cv']:.4f}")

    manifests = [submission_manifest(frames[n], n, {}, usable[n]["cv"], usable[n]["seeds"])
                 for n in (champion, hedge[0])]
    print("\nmanifests written:")
    for m in manifests:
        print(f"  {m['model']:12} hash {m['pred_hash']} | mean {m['pred_mean']:.4f} | "
              f"cv {m['cv_score']:.4f} | seeds {m['seeds']}")
    return champion, hedge[0], manifests

champion, hedge, manifests = final_two(candidates, sample_submission)
```

The broken candidate is rejected before it can be chosen, which matters because it has the
**highest CV score in the set** — exactly the shape of the real accident, where the file you most
want to submit is the one with something wrong in it. Validation runs before selection, never
after.

Here `broken` (CV 0.8200) fails on 65 NaN predictions. Among the four usable files, `blend` wins on
CV (0.8150), and `forest` becomes the hedge: its CV (0.8065) is within 0.01 of the champion and its
correlation with it (0.8269) is the lowest of the three.

The hedge rule is the other piece worth keeping. Picking the top two by CV score usually gives you
two nearly identical files, which wastes a submission slot: if the champion is wrong about the
test set, its near-twin is wrong the same way. Selecting the *least correlated* candidate within a
tolerance of the champion's score buys a genuinely different bet for a fraction of a point of
expected CV. Set that tolerance from your own noise measurement (ch. 2), not from taste — 0.01 is
right when fold noise is around 0.005 and far too generous when it is 0.0005.

Two habits that finish the job. Write the manifest **at submission time**, not afterwards, so the
hash is computed from the bytes you actually uploaded. And keep the previous best on disk so the
correlation check has something to compare against — it is the only check in the validator that
catches a positionally-misaligned file, and misalignment is the single most common way a good
model produces a terrible score.
