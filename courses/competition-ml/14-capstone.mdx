## The project

Enter a real tabular competition — an active Kaggle Playground season, a past competition with a
private leaderboard you can still submit against, or a dataset you split yourself into train and a
sealed test set — and run it the way this course describes: read the metric and audit the leaks
before modelling, build a validation scheme you can defend, engineer features in measured blocks,
train a diverse bank of models, combine them with a method whose optimism you have measured, and
ship two final submissions chosen by a rule you wrote down in advance. The deliverable is the pair
of submission files **and** the solution report that explains them. A high score with no report is
half the work; a report whose numbers do not reproduce is none of it.

## Hard constraints (no vibe coding)

- **No AI assistants** for the code, the feature ideas, or the write-up. Read the competition
  discussion forum after you finish, not before — the point is to arrive at the decisions
  yourself.
- **No copied public notebooks.** You may use scikit-learn, a gradient-boosting library, Optuna,
  pandas and NumPy. You may not fork someone else's pipeline.
- **Implement from scratch**, using libraries only to check your work: the target encoder, the
  adversarial-validation harness, the blend-weight fitter, the hill-climbing selector, the
  submission validator, and the report generator.
- **Every number in the report comes from a run in your run store.** No remembered scores, no
  numbers typed by hand.
- **The final-two selection rule is written down before you see the last leaderboard update**, and
  you follow it even when you do not like the answer.
- **Determinism is a requirement.** Re-running your pipeline from its config reproduces the
  submission file byte for byte, verified by its hash.

## What it must contain (and the chapter each tests)

1. **A competition brief** produced before any modelling: metric family and what it rewards, a
   leak audit across the four families (identifier, row order, duplicates, groups), and the
   validation scheme you chose with the evidence for it. (ch. 1)
2. **A validation scheme you can defend numerically**: the fold structure, its noise level
   measured across repeats, and the resolution of the public leaderboard computed from its size —
   plus the weight you will give the leaderboard in any decision. (ch. 2)
3. **A baseline ladder** from constant predictor to gradient boosting, with the gaps read as
   diagnostics, and a learning curve that sets the subsample size you iterate at. (ch. 3)
4. **Feature blocks added and measured one at a time**, with an ablation table showing what each
   block is worth *given the others*, not just in the order you added them. (ch. 4)
5. **Out-of-fold target encoding** for at least one high-cardinality column, with smoothing tuned
   by cross-validation and an unseen-category fallback that you have tested. (ch. 5)
6. **A column-relationship pass**: what each anonymised or opaque column is, exact relationships
   between columns, missingness blocks, and — if the data has one — a reconstructed entity key
   with aggregations built on it. (ch. 6)
7. **A model bank of at least five genuinely different models**, with the error-correlation matrix
   printed and read before any blending. (ch. 7)
8. **A blend whose operator and weights were chosen honestly**: the operator matched to the metric,
   the weights fitted inside folds, and the optimism of the naive version reported alongside.
   (ch. 8, ch. 11)
9. **A pseudo-labeling experiment**, run correctly (labels regenerated inside every fold, one
   round, soft labels) and reported *whether or not it helped* — with a decision rule, not a
   hope. (ch. 9)
10. **An adversarial-validation report**: overall and per-feature drift, what you did about the
    features that drift, and a note on whether the test-like validation set was worth building.
    (ch. 10)
11. **A submission pipeline** that merges on the key, validates structurally, compares against the
    previous best, and writes a manifest with a prediction hash. (ch. 12)
12. **A generated solution report** with all seven sections, a noise filter that demotes gains
    inside the fold-mean standard error, an ablation consistency check, and a claims linter run
    over the final text. (ch. 13)

## Acceptance criteria

- **Reproducibility.** `python run.py --config configs/final.yaml` regenerates both submission
  files with the hashes recorded in their manifests, on a machine that has only your repository.
- **Validation honesty.** The gap between your final CV estimate and your private-leaderboard
  score is smaller than three times your measured fold-mean standard error — or, if it is not, the
  report contains a diagnosis of why, written from evidence.
- **Leak-free.** Every fitted transformation — imputation, encoding, selection, calibration,
  pseudo-labels, blend weights — is refitted inside the folds. Demonstrate this by scoring a
  pure-noise version of your target through the whole pipeline and showing it lands at chance.
- **Measured features.** Every feature block in the final model has an ablation number attached,
  and every block whose ablation number is inside the noise band has been removed.
- **A real ensemble.** The final blend beats its best single member on honest cross-validation by
  more than the fold-mean standard error, and the report states the error correlation between its
  members.
- **Honest optimism accounting.** The report states the naive and honest estimates for the blend
  and the difference between them.
- **Two distinct finals.** The two submitted files have a prediction correlation below 0.95, and
  the rule that chose them was written before the last leaderboard refresh.
- **The report stands alone.** A reader who has not seen your code can state your validation
  scheme, the three things that mattered, the three that did not, and how to reproduce the result.

## Skills checklist (tick before you claim done)

- [ ] I can read a metric and say what it rewards and what it ignores.
- [ ] I can audit a dataset for the four leak families and act on what I find.
- [ ] I can pick a CV scheme from the structure of the data and defend it against the leaderboard.
- [ ] I can compute what difference a public leaderboard of size $n$ can actually resolve.
- [ ] I can build a baseline ladder and read its gaps as a plan.
- [ ] I can name six feature-engineering patterns and measure each one's contribution.
- [ ] I can implement out-of-fold target encoding with smoothing and an unseen-category fallback.
- [ ] I can reconstruct a hidden entity key from anonymised columns and verify it.
- [ ] I can read an error-correlation matrix and predict which model will help the ensemble.
- [ ] I can choose a blend operator from the metric rather than from habit.
- [ ] I can fit blend weights, measure their optimism, and shrink them when it matters.
- [ ] I can implement greedy ensemble selection and explain why it overfits less than optimisation.
- [ ] I can run pseudo-labeling without leaking, and decide from evidence whether to keep it.
- [ ] I can detect train/test drift and choose between dropping, weighting, and re-validating.
- [ ] I can separate seed noise from a real improvement.
- [ ] I can build a submission file that is aligned by key and validated before upload.
- [ ] I can generate a solution report whose every claim traces to a run.
