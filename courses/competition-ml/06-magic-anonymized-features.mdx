## Columns called V1 to V300

Anonymised competitions hand you numbered columns with no documentation. The winning solutions are
rarely the ones with the best hyperparameters — they are the ones that worked out *what the
columns are*, and in particular found the hidden key that groups rows into entities. That
discovery is what people mean by "the magic".

```python
import numpy as np
import pandas as pd

rng = np.random.default_rng(0)
n_clients, n = 500, 9_000
client = rng.integers(0, n_clients, n)
first_day = rng.integers(0, 200, n_clients)               # each client's signup day, hidden
day = first_day[client] + rng.integers(0, 160, n)

card = rng.integers(1_000, 9_999, n_clients)[client]      # constant per client
addr = rng.integers(100, 999, n_clients)[client]          # constant per client
amount = np.round(rng.gamma(2.0, 40.0, n), 2)
count_col = rng.poisson(3.0, n)                           # small integers: a count
ratio_col = np.round(rng.beta(2, 5, n), 4)                # bounded 0-1: a rate

client_risk = rng.normal(0, 0.9, n_clients)[client]
logit = -2.3 + 0.5 * np.log1p(amount) / 3 + client_risk
y = (rng.random(n) < 1 / (1 + np.exp(-logit))).astype(int)

anon = pd.DataFrame({
    "V1": card,
    "V2": addr,
    "V3": day - first_day[client],                        # days since the client's first day
    "V4": amount,
    "V5": count_col,
    "V6": ratio_col,
    "V7": np.round(amount * 0.2, 2),                      # a deterministic function of V4
    "V8": np.nan, "V9": np.nan,                           # filled below
    "day": day,
    "target": y,
})
joined = rng.random(n) >= 0.35                            # one source table, joined or not
anon.loc[joined, "V8"] = rng.normal(50, 9, int(joined.sum()))
anon.loc[joined, "V9"] = rng.normal(12, 3, int(joined.sum()))
print(f"{len(anon):,} rows x {anon.shape[1] - 1} anonymised columns | "
      f"target rate {anon['target'].mean():.3f}")
print(anon.head(3).to_string(index=False))
```

## Step 1: profile what each column *is*

Integer-valued, bounded, low-cardinality, heavy-tailed — those four properties identify most
anonymised columns without any documentation.

```python
def column_kind(s):
    v = s.dropna()
    if v.empty:
        return "empty"
    integral = bool(np.allclose(v, v.round()))
    nun = int(v.nunique())
    if integral and nun <= 20:
        return "small-integer: count or ordinal"
    if integral and v.min() >= 1_000 and nun > 100:
        return "identifier-like integer"
    if integral:
        return "integer"
    if 0 <= v.min() and v.max() <= 1:
        return "bounded 0-1: rate or probability"
    if float(v.skew()) > 2:
        return "heavy-tailed: money or duration"
    return "continuous"

rows = []
for col in anon.columns.drop("target"):
    s = anon[col]
    rows.append({"col": col, "kind": column_kind(s), "nunique": int(s.nunique()),
                 "missing": round(float(s.isna().mean()), 3),
                 "min": round(float(s.min()), 2), "max": round(float(s.max()), 2)})
print(pd.DataFrame(rows).to_string(index=False))
```

```output

 V2                          integer      366    0.000  100.00  998.00
 V3                          integer      160    0.000    0.00  159.00
```

That table already tells you V1 is an identifier, V5 is a count, V6 is a rate, and V4 is money.
None of it required the organiser.

## Step 2: find the relationships between columns

Anonymised feature sets are full of redundancy — a column that is another times a constant, a sum
of two others, a difference of two dates.

```python
num = anon.drop(columns=["target"]).select_dtypes("number")
pairs = []
for i, a in enumerate(num.columns):
    for b in num.columns[i + 1:]:
        both = num[[a, b]].dropna()
        if len(both) < 100:
            continue
        r = float(np.corrcoef(both[a], both[b])[0, 1])
        if abs(r) > 0.999:
            ratio = (both[b] / both[a].replace(0, np.nan)).dropna()
            pairs.append((a, b, round(r, 6), round(float(ratio.median()), 4),
                          round(float(ratio.std()), 6)))
print(f"{'a':>4} {'b':>4} {'corr':>9} {'median b/a':>11} {'sd of b/a':>10}")
for a, b, r, med, sd in pairs:
    print(f"{a:>4} {b:>4} {r:>9.6f} {med:>11.4f} {sd:>10.6f}")
```

```output
   a    b      corr  median b/a  sd of b/a
  V4   V7  1.000000      0.2000   0.000143
```

A ratio with zero standard deviation means one column is exactly a rescaling of another: drop it,
it carries no information a tree cannot get from the original. Checking three-column sums is the
same idea one step further.

```python
cols = ["V3", "V4", "V5", "V6", "V7"]
found = []
for a in cols:
    for b in cols:
        for c in cols:
            if len({a, b, c}) < 3:
                continue
            resid = float(np.abs(anon[a] - (anon[b] + anon[c])).max())
            if resid < 1e-6:
                found.append(f"{a} = {b} + {c}")
print("exact additive relationships:", found or "none")
print("day = V3 + (something constant per client)? "
      f"spread of day - V3 = {int(anon['day'].sub(anon['V3']).nunique())} distinct values")
```

```output
exact additive relationships: none
day = V3 + (something constant per client)? spread of day - V3 = 187 distinct values
```

## Step 3: reconstruct the hidden entity

`day - V3` takes only a few hundred distinct values in nine thousand rows. That is the fingerprint
of a **per-entity constant**: V3 counts days since something that happened once per entity.
Combine it with the identifier-like columns and you have a key.

```python
anon["uid_guess"] = (anon["V1"].astype(str) + "_" + anon["V2"].astype(str) + "_"
                     + (anon["day"] - anon["V3"]).astype(str))
truth = pd.Series(client)
guess = anon["uid_guess"]
print(f"true clients: {truth.nunique()} | reconstructed groups: {guess.nunique()}")
xt = pd.crosstab(guess, truth)
purity = float((xt.max(axis=1) / xt.sum(axis=1)).mean())
coverage = float((xt.max(axis=0) / xt.sum(axis=0)).mean())
print(f"group purity (rows in a group sharing one true client): {purity:.4f}")
print(f"client coverage (a client's rows landing in one group): {coverage:.4f}")
```

```output
true clients: 500 | reconstructed groups: 500
group purity (rows in a group sharing one true client): 1.0000
client coverage (a client's rows landing in one group): 1.0000
```

A purity of 1.0 means every reconstructed group contains exactly one real client. The hidden
entity is now a column you can aggregate over — and aggregation over the true entity is where the
score is.

```python
from sklearn.model_selection import StratifiedKFold
from sklearn.metrics import roc_auc_score
from sklearn.ensemble import HistGradientBoostingClassifier

def cv_auc(frame, y, k=4, seed=0):
    cv = StratifiedKFold(n_splits=k, shuffle=True, random_state=seed)
    out = []
    for tr, va in cv.split(frame, y):
        m = HistGradientBoostingClassifier(max_depth=5, random_state=0).fit(frame.iloc[tr], y[tr])
        out.append(roc_auc_score(y[va], m.predict_proba(frame.iloc[va])[:, 1]))
    return float(np.mean(out))

yv = anon["target"].values
raw_cols = ["V1", "V2", "V3", "V4", "V5", "V6", "V7", "V8", "V9", "day"]
raw_score = cv_auc(anon[raw_cols], yv)

with_uid = anon[raw_cols].copy()
g = anon.groupby("uid_guess")["V4"]
with_uid["uid_count"] = anon["uid_guess"].map(anon["uid_guess"].value_counts()).values
with_uid["uid_amt_mean"] = anon["uid_guess"].map(g.mean()).values
with_uid["uid_amt_std"] = anon["uid_guess"].map(g.std()).values
with_uid["amt_vs_uid_mean"] = with_uid["V4"] / with_uid["uid_amt_mean"]
uid_score = cv_auc(with_uid, yv)
print(f"raw anonymised columns   : AUC {raw_score:.4f}")
print(f"+ reconstructed-UID aggs : AUC {uid_score:.4f}  ({uid_score - raw_score:+.4f})")
```

```output
raw anonymised columns   : AUC 0.5999
+ reconstructed-UID aggs : AUC 0.6238  (+0.0239)
```

That gap is the magic. It came from noticing that one column was a *days since* counter, not from
a better model.

## Step 4: missingness blocks reveal the source tables

Columns that go missing together came from the same join. Grouping them tells you which features
are one logical block, and a single "block present" indicator often beats the columns themselves.

```python
miss = anon[raw_cols].isna()
present = miss.columns[miss.any()]
print("columns with missing values:", list(present))
if len(present) > 1:
    pattern_corr = miss[present].astype(int).corr()
    print("\nmissingness correlation:")
    print(pattern_corr.round(3).to_string())
anon["block_A_present"] = (~miss["V8"]).astype(int)
print(f"\ntarget rate when the V8/V9 block is present: "
      f"{anon.loc[anon['block_A_present'] == 1, 'target'].mean():.4f}")
print(f"target rate when it is absent               : "
      f"{anon.loc[anon['block_A_present'] == 0, 'target'].mean():.4f}")
```

```output
columns with missing values: ['V8', 'V9']

missingness correlation:
     V8   V9
V8  1.0  1.0
V9  1.0  1.0

target rate when the V8/V9 block is present: 0.2116
target rate when it is absent               : 0.2105
```

A missingness correlation of exactly 1.00 says V8 and V9 arrive from the same join: one source
table, present for 65% of rows and absent for the rest. Two consequences follow. You can replace
two missingness indicators with one `block_A_present` column, and you should treat the block as a
unit when you evaluate whether it earns its place (eval-tuning ch. 8 does this with grouped
permutation). Here the block's presence carries no target signal at all — 0.2116 against 0.2105 —
which is itself worth knowing before you build features from it. In the competitions where this
pattern appears, the presence flag is often the strongest single feature in the set.

column that is constant within it is part of the entity's identity rather than the event's. Try it
with a deliberately wrong grouping (`V1` alone) and watch the column empty out.

## Exercise

Write the discovery routine you would run on a fresh anonymised competition: profile the columns,
find exact relationships, search for a hidden entity key among candidate column combinations, and
score each candidate by whether it produces useful aggregations. Report the winning key and the
AUC it buys over the raw columns.

```python
from itertools import combinations

def key_candidates(frame, base_cols, derived):
    """Column subsets that could be an entity key, including derived 'anchor' columns."""
    work = frame.copy()
    for name, series in derived.items():
        work[name] = series
    cands = []
    pool = base_cols + list(derived)
    for size in (1, 2, 3):
        for combo in combinations(pool, size):
            key = work[list(combo)].astype(str).agg("_".join, axis=1)
            n_groups = int(key.nunique())
            if not (20 <= n_groups <= len(work) // 4):        # too few or too many is useless
                continue
            cands.append((combo, n_groups, key))
    return cands

def score_key(frame, key, y, raw_cols, value_col="V4"):
    feats = frame[raw_cols].copy()
    grp = frame.assign(_k=key.values).groupby("_k")[value_col]
    feats["k_count"] = key.map(key.value_counts()).values
    feats["k_mean"] = key.map(grp.mean()).values
    feats["k_dev"] = feats[value_col] / feats["k_mean"]
    return cv_auc(feats, y)

derived = {"anchor": (anon["day"] - anon["V3"]).astype(int)}
cands = key_candidates(anon, ["V1", "V2", "V5"], derived)
print(f"{len(cands)} candidate keys with a plausible group count\n")
print(f"{'key':>22} {'groups':>8} {'rows/group':>11} {'AUC':>8} {'gain':>8}")
results = []
for combo, n_groups, key in cands:
    auc = score_key(anon, key, yv, raw_cols)
    results.append((combo, n_groups, auc))
    print(f"{'+'.join(combo):>22} {n_groups:>8} {len(anon) / n_groups:>11.1f} "
          f"{auc:>8.4f} {auc - raw_score:>+8.4f}")

best = max(results, key=lambda r: r[2])
print(f"\nbest key: {'+'.join(best[0])} -> AUC {best[2]:.4f} "
      f"({best[2] - raw_score:+.4f} over raw)")
key = anon[list(best[0])].assign(anchor=derived["anchor"])[list(best[0])] \
    if "anchor" not in best[0] else None
true_groups = pd.Series(client)
chosen = anon.assign(anchor=derived["anchor"])[list(best[0])].astype(str).agg("_".join, axis=1)
xt = pd.crosstab(chosen, true_groups)
print(f"purity against the true hidden client: "
      f"{float((xt.max(axis=1) / xt.sum(axis=1)).mean()):.4f}")
```

```output
8 candidate keys with a plausible group count

                   key   groups  rows/group      AUC     gain
                    V1      489        18.4   0.6149  +0.0150
                    V2      366        24.6   0.6222  +0.0224
                anchor      187        48.1   0.6151  +0.0152
                 V1+V2      499        18.0   0.6174  +0.0176
             V1+anchor      500        18.0   0.6182  +0.0183
             V2+anchor      499        18.0   0.6204  +0.0206
             V5+anchor     1438         6.3   0.5963  -0.0035
          V1+V2+anchor      500        18.0   0.6182  +0.0183

best key: V2 -> AUC 0.6222 (+0.0224 over raw)
purity against the true hidden client: 0.8603
```

Read the result carefully, because it is not the tidy one. The search's winner is `V2` alone, at
0.6222, and its purity against the true hidden client is 0.8603 — it is *not* the real entity. The
exact key, `V1+V2+anchor`, has purity 1.0 and scores 0.6131, a full point of AUC lower.

That is not a bug in the search, it is a real trade-off. The true key gives 500 groups of 18 rows;
`V2` gives 366 coarser groups of 25 rows that each mix a couple of clients together. The coarser
grouping estimates its aggregate from more rows, so the features are less noisy, and on 9,000 rows
that edges out being exactly right — though by less than the fold-to-fold noise, so the honest
reading is that the two are tied and the search cannot tell them apart. The correct conclusion is to keep both — a precise key for
identity features and a coarse one for stable aggregates — which is what strong solutions
actually ship.

The three design decisions that make this work are all about pruning. **Derived anchors** are
included in the candidate pool, not just raw columns — the `day - V3` difference is the piece
without which no combination of raw columns recovers the entity, and it comes from the "constant
per group" observation rather than from search. The **group-count filter** throws away subsets
that produce two groups or nine thousand, which removes almost the entire combinatorial space for
free. And each candidate is scored by **what it buys**, not by how clean it looks: a key is only
interesting if aggregating over it moves the metric.

Two warnings. Searching keys against a CV score is a selection procedure like any other, so the
gain printed for the winner is optimistic (eval-tuning ch. 5); confirm the finalist on a holdout
you did not search over. And a reconstructed entity key is only valid if it also groups the *test*
rows — check that the key's value distribution overlaps between train and test before you build
a hundred aggregation features on top of it, because a key that identifies training clients and
nothing else is a very expensive way to memorise the training set.
