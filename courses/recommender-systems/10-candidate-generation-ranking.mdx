## One model cannot score the whole catalogue

Picture a shop assistant asked to pick ten books for you from a warehouse of ten million. They
do not read every blurb. They grab a few hundred plausible ones fast — bestsellers, books like the
ones you bought, new arrivals — and then look carefully at that pile. Every large recommender is
built the same way: a cheap **candidate generation** stage that touches the whole catalogue, and an
expensive **ranking** stage that touches only what stage one hands it.

The reason is arithmetic, not taste. Fix a latency budget per request and a cost per scored
(user, item) pair, and the number of items each model can afford to look at falls out directly.

```python
catalogue, budget_ms = 10_000_000, 100
stages = [  # (stage, microseconds per (user, item) scored) -- order-of-magnitude assumptions
    ("dot product, d=64, brute force", 0.02),
    ("GBDT ranker, 500 trees x depth 8", 5.0),
    ("deep cross-feature ranker (MLP over 300 features)", 40.0),
    ("transformer cross-encoder over user history", 2_000.0),
]
print(f"{'model':>50} {'items in 100 ms':>16} {'full catalogue':>15}")
for name, us in stages:
    print(f"{name:>50} {budget_ms * 1_000 / us:>16,.0f} {catalogue * us / 1e6:>13,.1f} s")
funnel = [("ANN retrieval", catalogue, 0.0), ("light ranker", 2_000, 5.0),
          ("heavy ranker", 300, 40.0), ("re-rank / rules", 50, 0.0)]
print("\nfunnel:", " -> ".join(f"{n} ({k:,})" for n, k, _ in funnel))
print(f"model time of the two rankers: {sum(k * us for _, k, us in funnel) / 1_000:.1f} ms")
```

```output
                                             model  items in 100 ms  full catalogue
                    dot product, d=64, brute force        5,000,000           0.2 s
                  GBDT ranker, 500 trees x depth 8           20,000          50.0 s
 deep cross-feature ranker (MLP over 300 features)            2,500         400.0 s
       transformer cross-encoder over user history               50      20,000.0 s

funnel: ANN retrieval (10,000,000) -> light ranker (2,000) -> heavy ranker (300) -> re-rank / rules (50)
model time of the two rankers: 22.0 ms
```

Read the first table as "how many items can this model afford to see". A dot product can cover
five million items inside 100 ms, so a two-tower retriever (ch. 7) plus an index can face the whole
catalogue. A 500-tree GBDT can afford 20,000 items and would need 50 seconds for all ten million; a
cross-encoder over the user's history can afford 50. No single model is both cheap enough for the
catalogue and rich enough to use cross features between user and item.

The funnel resolves this: each stage cuts the set by one or two orders of magnitude so the next,
more expensive stage spends its budget only where it matters. Two rankers over 2,000 and 300 items
cost 22 ms of model time — well inside the budget, and leaving room for feature fetching, which in
practice costs more than the model.

## Three time windows, not two

A ranker learns from examples of the form "this candidate was shown to this user, and they did or
did not take it". To build those examples honestly you need a past to compute features from and a
*later* period to read labels from, and then a third, still later period to test on. Every chapter
so far used two windows; this one needs three.

```python
import numpy as np
import pandas as pd
import torch
import torch.nn as nn
from scipy import sparse

torch.manual_seed(0)
torch.set_num_threads(1)
rng = np.random.default_rng(0)

n_users, n_items = 2_500, 900
user_taste = rng.normal(0, 1, (n_users, 4))
genre = rng.integers(0, 6, n_items)
item_style = rng.normal(0, 1.4, (6, 4))[genre] + rng.normal(0, 0.35, (n_items, 4))
activity = rng.lognormal(-0.4, 1.0, n_users)
exposure = rng.lognormal(-1.0, 1.7, n_items) * np.where(genre == 0, 4.0, 1.0)

months = []
for month in range(12):
    user_taste = user_taste + rng.normal(0, 0.25, (n_users, 4))
    logit = (user_taste @ item_style.T / 2 - 4.0
             + np.log(activity)[:, None] + np.log(exposure)[None, :])
    r, c = np.nonzero(rng.random((n_users, n_items)) < 1 / (1 + np.exp(-logit)) / 12)
    months.append(pd.DataFrame({"user": r, "item": c,
                                "ts": month * 30 + rng.integers(0, 30, len(r))}))
events = pd.concat(months).sort_values("ts").reset_index(drop=True)

t2 = events["ts"].max() - 60          # test window starts after t2 (same split as ch. 5-7)
t1 = t2 - 60                          # ranker-label window is (t1, t2]
hist_A = events[events["ts"] <= t1]
lab_B = events[(events["ts"] > t1) & (events["ts"] <= t2)]
hist_AB = events[events["ts"] <= t2]
test_C = events[events["ts"] > t2]
for name, df in (("history A (ranker features)", hist_A), ("window B (ranker labels)", lab_B),
                 ("history A+B (serving features)", hist_AB), ("window C (test)", test_C)):
    print(f"{name:>32}: {len(df):>7,} events, days {df['ts'].min():>3}-{df['ts'].max():>3}")
```

```output
     history A (ranker features):  80,818 events, days   0-239
        window B (ranker labels):  22,598 events, days 240-299
  history A+B (serving features): 103,416 events, days   0-299
                 window C (test):  23,087 events, days 300-359
```

Window A plays the role of "everything known when the ranker's training candidates were
generated", window B supplies the labels for those candidates, and at serving time the whole
pipeline is rebuilt on A+B and tested on window C. The test split is identical to chapters 5–7, so
numbers here are directly comparable with theirs.

## Several retrievers, one candidate set

No single retriever sees everything. Popularity knows what is broadly liked, item-item CF (ch. 3)
knows "people who took X also took Y", iALS (ch. 5) knows your latent taste, and a trending source
knows what is hot *this week*. Production systems run several of these in parallel, take the top
$n$ from each, and merge them into one deduplicated candidate set $C_u$ for user $u$.

The code below builds four sources on a given history: global popularity, **trend** (popularity
with each event down-weighted by a 14-day half-life, so last week counts more than last year),
item-item cosine CF, and iALS. It also builds two recency-weighted variants (30-day half-life) of
the CF and iALS scores — not as sources, but as features the ranker will use later.

```python
def implicit_als(X, d=16, alpha=5.0, lam=50.0, n_iter=8, seed=0):
    """Weighted ALS from ch. 5 (Hu, Koren, Volinsky)."""
    U = np.random.default_rng(seed).normal(0, 0.01, (X.shape[0], d))
    V = np.random.default_rng(seed + 1).normal(0, 0.01, (X.shape[1], d))
    Xt, eye = X.T.tocsr(), lam * np.eye(d)
    for _ in range(n_iter):
        for M, F, O in ((X, U, V), (Xt, V, U)):
            G = O.T @ O + eye
            for row in range(M.shape[0]):
                idx = M.indices[M.indptr[row]:M.indptr[row + 1]]
                if len(idx) == 0:
                    F[row] = 0
                    continue
                Oi = O[idx]
                F[row] = np.linalg.solve(G + alpha * Oi.T @ Oi, (1 + alpha) * Oi.sum(0))
    return U, V

def item_stats(hist, now, half_life=14.0):
    pop = np.bincount(hist["item"], minlength=n_items).astype(float)
    w = 0.5 ** (np.abs(now - hist["ts"].values) / half_life)
    trend = np.bincount(hist["item"], weights=w, minlength=n_items)
    last = np.full(n_items, -1_000.0)
    np.maximum.at(last, hist["item"].values, hist["ts"].values.astype(float))
    return {"pop": pop, "trend": trend, "age": now - last}

def build_sources(hist, now):
    X = sparse.csr_matrix((np.ones(len(hist)), (hist["user"], hist["item"])),
                          shape=(n_users, n_items))
    X.data[:] = 1.0
    C = (X.T @ X).toarray()
    norm = np.sqrt(np.diag(C)) + 1e-9
    S = C / norm[:, None] / norm[None, :]
    np.fill_diagonal(S, 0.0)
    U, V = implicit_als(X)
    w = 0.5 ** ((now - hist["ts"].values) / 30.0)          # recency weights, 30-day half-life
    Xw = sparse.csr_matrix((w, (hist["user"], hist["item"])), shape=(n_users, n_items))
    U_rec = np.zeros_like(U)                                # fold users in on recent history only
    for u in range(n_users):
        idx, wu = Xw.indices[Xw.indptr[u]:Xw.indptr[u + 1]], Xw.data[Xw.indptr[u]:Xw.indptr[u + 1]]
        if len(idx):
            Vi = V[idx]
            U_rec[u] = np.linalg.solve(V.T @ V + 50.0 * np.eye(V.shape[1])
                                       + 5.0 * (Vi * wu[:, None]).T @ Vi, Vi.T @ (1 + 5.0 * wu))
    src = {"seen": X.toarray() > 0, "icf": np.asarray(X @ S), "als": U @ V.T, "V": V, "X": X,
           "icf_recent": np.asarray(Xw @ S), "als_recent": U_rec @ V.T}
    src.update(item_stats(hist, now))
    return src

def generate(src, users, n_per):
    """Top-n_per unseen items from each source, merged and deduplicated."""
    seen = src["seen"][users]
    per_source = {}
    for name in ("pop", "trend", "icf", "als"):
        S = np.broadcast_to(src[name], (n_users, n_items))[users] if src[name].ndim == 1 \
            else src[name][users]
        per_source[name] = np.argpartition(-np.where(seen, -np.inf, S), n_per, axis=1)[:, :n_per]
    votes = np.zeros((len(users), n_items), dtype=np.int8)
    for idx in per_source.values():
        votes[np.arange(len(users))[:, None], idx] += 1
    return per_source, votes

src_A, src_AB = build_sources(hist_A, t1), build_sources(hist_AB, t2)
truth_B = {u: set(g) for u, g in lab_B.groupby("user")["item"]}
truth_C = {u: set(g) for u, g in test_C.groupby("user")["item"]}
users_tr = np.array([u for u in range(n_users) if truth_B.get(u) and src_A["seen"][u].any()])
users_te = np.array([u for u in range(n_users) if truth_C.get(u) and src_AB["seen"][u].any()])
per_te, votes_te = generate(src_AB, users_te, 50)
sizes = (votes_te > 0).sum(1)
print(f"ranker-train users {len(users_tr):,} | test users {len(users_te):,}")
print(f"4 sources x 50 = 200 slots -> {sizes.mean():.1f} unique candidates per user "
      f"(min {sizes.min()}, max {sizes.max()})")
print(f"items proposed by 1/2/3/4 sources: "
      + " / ".join(f"{(votes_te == k).sum() / len(users_te):.1f}" for k in (1, 2, 3, 4)))
```

```output
ranker-train users 2,395 | test users 2,381
4 sources x 50 = 200 slots -> 83.8 unique candidates per user (min 65, max 119)
items proposed by 1/2/3/4 sources: 22.8 / 26.9 / 13.1 / 21.0
```

Two hundred slots collapse to about 84 distinct items, so the sources overlap heavily — 21 items
per user are proposed by all four. That overlap is not waste: how many sources proposed an item
(`n_sources`, the "votes") is itself a useful ranking feature. The 23 items proposed by only one
source are where a second source earns its keep; the next section measures whether they do.

## Candidate recall is the ceiling

Stage one is not judged on ordering — the ranker will reorder everything anyway. It is judged on
one question: *did the items the user actually wanted make it into the pile?* That is candidate
recall at the pile size $N$,

$$
\mathrm{Recall@}N(u) = \frac{|C_u \cap T_u|}{|T_u|},
$$

where $C_u$ is the candidate set and $T_u$ the user's true future items (window C). Note the
denominator is $|T_u|$, not $\min(k, |T_u|)$ as in ch. 2: at $N$ in the hundreds you are asking
about coverage, not about a top-$k$ list.

```python
def cand_recall(sets, users, truth):
    return float(np.mean([len(sets[r] & truth[u]) / len(truth[u]) for r, u in enumerate(users)]))

print(f"{'source':>8} " + " ".join(f"{'R@' + str(n):>7}" for n in (10, 25, 50, 100)))
for name in ("pop", "trend", "icf", "als", "union"):
    row = []
    for n in (10, 25, 50, 100):
        per, votes = generate(src_AB, users_te, n)
        sets = ([set(np.flatnonzero(v)) for v in votes] if name == "union"
                else [set(x) for x in per[name]])
        row.append(cand_recall(sets, users_te, truth_C))
    print(f"{name:>8} " + " ".join(f"{x:>7.4f}" for x in row))
```

```output
  source    R@10    R@25    R@50   R@100
     pop  0.0852  0.1612  0.2540  0.3874
   trend  0.0838  0.1574  0.2514  0.3770
     icf  0.1029  0.1978  0.3048  0.4504
     als  0.1147  0.2231  0.3449  0.4927
   union  0.1711  0.2940  0.4193  0.5587
```

iALS is the best single source at every $N$ (0.3449 at 50), and popularity is not far behind —
this catalogue has a heavy head. But the union beats every source at the same per-source $n$: with
50 slots each it covers 0.4193 of the future, against 0.3449 for iALS alone.

Now compare at equal *pile size*, which is what the ranker's budget actually limits. The union at
$n=50$ is 84 items and recalls 0.4193; iALS alone at 100 items recalls 0.4927. Item for item,
going deeper into the best source beats merging here. That is a property of this dataset: it was
generated from latent taste plus popularity, which iALS already models, so the other sources mostly
add information iALS has. Extra sources pay for themselves when they carry *different* information
— content for new items (ch. 9), session context, social graph — and the only way to know is this
table, recomputed at equal $|C|$.

Also notice that more than 40% of the future is unreachable even at 155 candidates. Some of it is
repeat consumption of already-seen items, which every source filters out by design; the rest is
taste drift that no history-based retriever can foresee.

### Why stage one bounds every later stage

This short derivation shows that no ranker, however good, can score above a ceiling set entirely
by stage one. The final list $L_u$ is a subset of $C_u$, so its hits are a subset of the hits in
$C_u$:

$$
L_u \subseteq C_u \;\Rightarrow\; |L_u \cap T_u| \le |C_u \cap T_u|
\;\Rightarrow\; \mathrm{Recall@}k(u) \le \frac{|C_u \cap T_u|}{\min(k, |T_u|)}.
$$

For NDCG the best a ranker can do is put every hit in $C_u$ at the top, so

$$
\mathrm{NDCG@}k(u) \le \frac{\sum_{j=1}^{\min(k,\,|C_u \cap T_u|)} 1/\log_2(j+1)}
{\sum_{j=1}^{\min(k,\,|T_u|)} 1/\log_2(j+1)} =: \mathrm{NDCG}^{\text{oracle}}(u).
$$

The code computes that oracle ceiling, next to what you get by simply ordering the pile by the
iALS score.

```python
def ndcg_at_10(ranked, rel):
    dcg = sum(1 / np.log2(j + 2) for j, i in enumerate(ranked[:10]) if i in rel)
    return dcg / sum(1 / np.log2(j + 2) for j in range(min(10, len(rel))))

print(f"{'n per source':>12} {'|C|':>6} {'recall@|C|':>11} {'oracle NDCG@10':>15} "
      f"{'iALS-order NDCG@10':>19}")
for n in (5, 10, 25, 50, 100):
    _, votes = generate(src_AB, users_te, n)
    orc, als_nd = [], []
    for r, u in enumerate(users_te):
        c = np.flatnonzero(votes[r])
        hits = [i for i in c if i in truth_C[u]]
        orc.append(ndcg_at_10(hits, truth_C[u]))
        als_nd.append(ndcg_at_10(c[np.argsort(-src_AB["als"][u, c])], truth_C[u]))
    sets = [set(np.flatnonzero(v)) for v in votes]
    print(f"{n:>12} {(votes > 0).sum(1).mean():>6.1f} {cand_recall(sets, users_te, truth_C):>11.4f} "
          f"{np.mean(orc):>15.4f} {np.mean(als_nd):>19.4f}")
```

```output
n per source    |C|  recall@|C|  oracle NDCG@10  iALS-order NDCG@10
           5   10.7      0.1124          0.2011              0.1073
          10   20.6      0.1711          0.2958              0.1136
          25   44.9      0.2940          0.4613              0.1136
          50   83.8      0.4193          0.6087              0.1136

```

The oracle column climbs from 0.2011 to 0.7407 as the pile grows: a perfect ranker would turn
more candidates into more NDCG. The iALS-order column does not move after $n=10$, and that is
expected — its top 10 are always in the pile, so the extra candidates sit below position 10 and
are never seen. At $n=5$ it drops to 0.1073 because the pile no longer contains iALS's own
top 10.

The gap between the two columns, 0.1136 against 0.6087 at $n=50$, is the space a ranker has to
work in. Most of it is unreachable in practice (the oracle cheats by reading the labels), but it
tells you which stage to blame. If the ranker is close to the oracle, improve retrieval; if it is
far below, improve the ranker.

## Approximate nearest neighbours: scan less, miss a little

With 900 items you can score every item exactly. With 100 million you cannot, even with a dot
product, so the embedding retrievers (iALS, the two-tower of ch. 7) sit behind an **approximate
nearest-neighbour (ANN) index**. The idea is a library's shelving: cluster the item vectors once,
and at query time only search the few clusters whose centre is closest to the query.

That is an **inverted-file (IVF)** index. Offline, run k-means to get $n_{\text{list}}$ centroids
and file every item under its nearest one. Online, score the query against the centroids, open
the $n_{\text{probe}}$ best lists, and do exact search inside them only. The knob $n_{\text{probe}}$
trades recall (of the true top-$k$) against work. Below: 100,000 clustered unit vectors, 256 lists,
cost counted as vectors scanned (centroids included) rather than seconds.

```python
rng_ann = np.random.default_rng(1)
n_vec, d_ann = 100_000, 32
centres = rng_ann.normal(0, 1, (400, d_ann))
base = centres[rng_ann.integers(0, 400, n_vec)] + rng_ann.normal(0, 0.6, (n_vec, d_ann))
base /= np.linalg.norm(base, axis=1, keepdims=True)
queries = base[rng_ann.integers(0, n_vec, 200)] + rng_ann.normal(0, 0.3, (200, d_ann))
queries /= np.linalg.norm(queries, axis=1, keepdims=True)
exact = np.argpartition(-(queries @ base.T), 10, axis=1)[:, :10]

def kmeans(Z, k, iters=10, seed=0):
    r = np.random.default_rng(seed)
    cent = Z[r.choice(len(Z), k, replace=False)]
    for _ in range(iters):
        assign = np.argmax(Z @ cent.T, axis=1)
        for j in range(k):
            members = Z[assign == j]
            if len(members):
                cent[j] = members.mean(0) / np.linalg.norm(members.mean(0))
    return cent

n_list = 256
cent = kmeans(base[rng_ann.choice(n_vec, 20_000, replace=False)], n_list)
assign = np.argmax(base @ cent.T, axis=1)
lists = [np.flatnonzero(assign == j) for j in range(n_list)]

def ivf_search(q, n_probe, k=10):
    probe = np.argsort(-(cent @ q))[:n_probe]
    cand = np.concatenate([lists[j] for j in probe])
    top = cand[np.argpartition(-(base[cand] @ q), min(k, len(cand) - 1))[:k]]
    return top, len(cand)

print(f"{'n_probe':>8} {'recall@10':>10} {'vectors scanned':>16} {'share of brute force':>21}")
for n_probe in (1, 2, 4, 8, 16, 32):
    rec, scanned = [], []
    for qi, q in enumerate(queries):
        top, n_scan = ivf_search(q, n_probe)
        rec.append(len(set(top) & set(exact[qi])) / 10)
        scanned.append(n_scan + n_list)
    print(f"{n_probe:>8} {np.mean(rec):>10.4f} {np.mean(scanned):>16,.0f} "
          f"{np.mean(scanned) / n_vec:>21.2%}")
```

```output
 n_probe  recall@10  vectors scanned  share of brute force
       1     0.4525              642                 0.64%
       2     0.5810            1,039                 1.04%
       4     0.7080            1,800                 1.80%
       8     0.8265            3,429                 3.43%
      16     0.9170            6,561                 6.56%
      32     0.9705           12,764                12.76%
```

Opening one list scans 0.64% of the vectors and finds 45% of the true top 10; opening 32 scans
12.76% and finds 97%. The curve is concave — the last few percent of recall are the expensive ones,
because true neighbours that sit near a cluster boundary were filed in a list whose centroid looks
mediocre from the query. Production indexes add tricks on top: **product quantisation** (IVF-PQ in
FAISS) compresses each vector to a few bytes so the scan itself is cheaper, and **HNSW** replaces
clustering with a navigable small-world graph that gets 95%+ recall at very low scan counts, at the
price of memory and slow inserts.

The ANN recall multiplies into everything downstream. An index at 0.92 recall feeding a retriever
at candidate recall 0.34 gives roughly 0.31 if the misses are independent, so tune
$n_{\text{probe}}$ against the end-to-end metric, not the index benchmark.

## The ranker's training table, built across a time gap

The ranker is a supervised model, so it needs rows and labels. Each row is one (user, candidate)
pair that stage one actually produced; the label says whether the user took that item in the
*next* window. Training on the candidates retrieval really emits matters: those are the hard
negatives the ranker will face in production, not random catalogue items it could reject on
popularity alone.

Features come in three kinds. **Retrieval scores**: the iALS and CF scores, their recent-weighted
versions, and their rank in the user's list. **Item features**: log popularity, trend, the ratio of
the two (is the item rising?), days since anyone last touched it. **User–item affinity**: the
share of the user's history in the candidate's genre, overall and recency-weighted, plus how many
sources voted for the item. One user-only feature, history length, is included on purpose — watch
what it does to the pointwise model.

```python
FEATS = ["als", "icf", "als_recent", "icf_recent", "als_rank", "icf_rank", "log_pop",
         "log_trend", "trend_ratio", "log_item_age", "user_log_n", "genre_aff", "genre_aff_recent", "n_sources"]

def rank_matrix(S, seen):
    order = np.argsort(-np.where(seen, -np.inf, S), axis=1)
    rk = np.empty_like(order)
    np.put_along_axis(rk, order, np.arange(S.shape[1])[None, :].repeat(len(S), 0), axis=1)
    return rk

def feature_table(src, hist, now, users, truth, n_per=50, agg_hist=None):
    """One row per (user, candidate). agg_hist lets you (wrongly) compute aggregates on another log."""
    agg = hist if agg_hist is None else agg_hist
    it = src if agg_hist is None else item_stats(agg, now)
    _, votes = generate(src, users, n_per)
    r_idx, i_idx = np.nonzero(votes)
    u_idx = users[r_idx]
    seen = src["seen"][users]
    G = np.zeros((n_users, 6))
    np.add.at(G, (agg["user"].values, genre[agg["item"].values]), 1.0)
    Gr = np.zeros((n_users, 6))
    np.add.at(Gr, (agg["user"].values, genre[agg["item"].values]),
              0.5 ** (np.abs(now - agg["ts"].values) / 14.0))
    n_u = G.sum(1)
    df = pd.DataFrame({
        "user": u_idx, "item": i_idx,
        "als": src["als"][u_idx, i_idx], "icf": src["icf"][u_idx, i_idx],
        "als_recent": src["als_recent"][u_idx, i_idx], "icf_recent": src["icf_recent"][u_idx, i_idx],
        "als_rank": np.log1p(rank_matrix(src["als"][users], seen)[r_idx, i_idx]),
        "icf_rank": np.log1p(rank_matrix(src["icf"][users], seen)[r_idx, i_idx]),
        "log_pop": np.log1p(it["pop"][i_idx]), "log_trend": np.log1p(it["trend"][i_idx]),

        "user_log_n": np.log1p(n_u[u_idx]),
        "genre_aff": G[u_idx, genre[i_idx]] / np.maximum(n_u[u_idx], 1),
        "genre_aff_recent": Gr[u_idx, genre[i_idx]] / np.maximum(Gr[u_idx].sum(1), 1e-9),
        "n_sources": votes[r_idx, i_idx].astype(float),
    })
    df["label"] = [int(i in truth[u]) for u, i in zip(df["user"], df["item"])]
    return df
```

## Pointwise: classify each candidate on its own

The simplest ranker ignores that rows come in lists. Treat every (user, candidate) row as an
independent binary example, fit $P(y=1 \mid \mathbf{x})$ with log-loss, and sort each user's
candidates by the predicted probability. This is **pointwise** learning to rank, and it is what
most production rankers start as — a logistic model or GBDT on a click label.


which users click a lot is a large, easy part of the log-loss that contributes nothing to NDCG.
The GBDT, with more capacity, spends more of it on between-user structure and on overfitting
noisy interactions. Ranking metrics only care about order *within* a list, and the next losses are
built to see exactly that.

## Pairwise and listwise: losses that only see order

A pairwise loss asks a question the user's identity cannot answer: *of these two candidates for
the same user, which one did they take?* Anything constant within the user — history length,
general click-happiness — cancels out of that comparison, so the model cannot waste capacity on
it. A listwise loss goes one step further and scores the whole candidate list at once.

### From pairwise probabilities to lambdas

This derivation shows that LambdaRank is RankNet with each pair's gradient rescaled by how much
swapping that pair would change NDCG. Let $s_i$ be the model's score for candidate $i$ and suppose
the user preferred $i$ over $j$ (written $i \succ j$). **RankNet** (Burges et al., 2005) models
the probability of that preference with a logistic on the score difference and minimises its
negative log:

$$
P(i \succ j) = \sigma(s_i - s_j) = \frac{1}{1 + e^{-(s_i - s_j)}},
\qquad
C_{ij} = -\log \sigma(s_i - s_j) = \log\left(1 + e^{-(s_i - s_j)}\right).
$$

Differentiate with respect to the two scores. Using $\frac{d}{dz}\log(1+e^{-z}) = -\sigma(-z)$:

$$
\frac{\partial C_{ij}}{\partial s_i} = -\sigma\big(-(s_i - s_j)\big) =: \lambda_{ij},
\qquad
\frac{\partial C_{ij}}{\partial s_j} = -\lambda_{ij}.
$$

So each pair pushes $s_i$ up and $s_j$ down with force $|\lambda_{ij}|$, which is large when the
pair is mis-ordered and near zero when it is already well separated. The total force on item $i$
sums over all pairs it is in, $\lambda_i = \sum_{j: i \succ j} \lambda_{ij} - \sum_{j: j \succ i} \lambda_{ji}$,
and the gradient step is $s_i \leftarrow s_i - \eta\,\lambda_i$.

RankNet's flaw is that it counts every pair equally. Fixing a swap between positions 1 and 2 is
worth far more NDCG than fixing one between positions 70 and 71. **LambdaRank** (Burges et al.,
2006) never writes down a new loss; it rescales the gradient by the NDCG change from swapping $i$
and $j$ in the current ranking. With gain $g_i = 2^{y_i} - 1$ for label $y_i$, current positions
$r_i, r_j$ (1-based), and $\mathrm{IDCG}$ the DCG of the ideal ordering:

$$
|\Delta \mathrm{NDCG}_{ij}| = \frac{|g_i - g_j|\;\left|\dfrac{1}{\log_2(1 + r_i)} - \dfrac{1}{\log_2(1 + r_j)}\right|}{\mathrm{IDCG}},
\qquad
\boxed{\lambda_{ij}^{\text{Lambda}} = -\sigma\big(-(s_i - s_j)\big)\,|\Delta \mathrm{NDCG}_{ij}|}
$$

The $|\Delta\mathrm{NDCG}|$ factor depends on the current sort but not on the scores' values, so
you implement it as a *detached* weight on the RankNet pair loss: the autograd gradient is then
exactly $\lambda^{\text{Lambda}}$. Using $1/\log_2(1+r)$ only for $r \le k$ and zero beyond gives
the NDCG@$k$-targeted version; LightGBM's `objective="lambdarank"` is this gradient fed to boosted
trees (LambdaMART), with `lambdarank_truncation_level` playing the role of $k$.

### The listwise softmax

This one shows the listwise loss is a cross-entropy over the whole candidate list. Turn each
user's scores into a distribution over the list with a softmax, and match it to the label
distribution $p_i = y_i / \sum_{j} y_j$ (ListNet's top-one version, the same sampled-softmax shape
as ch. 7's in-batch loss):

$$
\mathcal{L}_u = -\sum_{i \in C_u} p_i \log \frac{e^{s_i}}{\sum_{j \in C_u} e^{s_j}},
\qquad
\frac{\partial \mathcal{L}_u}{\partial s_i} = \mathrm{softmax}(s)_i - p_i.
$$

The gradient is "predicted share minus true share", and adding a constant to every score in the
list changes nothing — the same invariance to user-level effects that the pairwise loss has.

The code trains one small MLP (two hidden layers) with each of the four losses on padded per-user
lists, so the only thing that differs is the objective.

```python
mu, sd = tr[FEATS].mean().values, tr[FEATS].std().values + 1e-9

def to_lists(df):
    groups = [g for _, g in df.groupby("user", sort=True)]
    L = max(len(g) for g in groups)
    Xl = np.zeros((len(groups), L, len(FEATS)), dtype=np.float32)
    Yl = np.zeros((len(groups), L), dtype=np.float32)
    Ml = np.zeros((len(groups), L), dtype=bool)
    for g_i, g in enumerate(groups):
        n = len(g)
        Xl[g_i, :n] = (g[FEATS].values - mu) / sd
        Yl[g_i, :n] = g["label"].values
        Ml[g_i, :n] = True
    return torch.as_tensor(Xl), torch.as_tensor(Yl), torch.as_tensor(Ml)

def ltr_loss(s, y, m, kind):
    if kind == "pointwise":
        return nn.functional.binary_cross_entropy_with_logits(s[m], y[m])
    if kind == "listwise":
        logp = torch.log_softmax(s.masked_fill(~m, -1e9), dim=1)
        has = y.sum(1) > 0
        return -((y * logp).sum(1)[has] / y.sum(1)[has]).mean()
    diff = s[:, :, None] - s[:, None, :]
    pair = (y[:, :, None] > y[:, None, :]) & m[:, :, None] & m[:, None, :]
    w = torch.ones_like(diff)
    if kind == "lambdarank":
        with torch.no_grad():
            rank = torch.argsort(torch.argsort(s.masked_fill(~m, -1e9), dim=1, descending=True), dim=1)
            disc = 1.0 / torch.log2(rank.float() + 2.0)
            n_pos = y.sum(1, keepdim=True).clamp(min=1).long()
            idcg = torch.cumsum(1.0 / torch.log2(torch.arange(s.shape[1]) + 2.0), 0)[n_pos - 1]
            w = (y[:, :, None] - y[:, None, :]).abs() * (disc[:, :, None] - disc[:, None, :]).abs()
            w = w / idcg[:, :, None]
    return (nn.functional.softplus(-diff) * w)[pair].sum() / pair.sum().clamp(min=1)

def train_ltr(kind, Xl, Yl, Ml, epochs=8, batch=64, lr=3e-3, seed=0):
    torch.manual_seed(seed)
    model = nn.Sequential(nn.Linear(len(FEATS), 64), nn.ReLU(), nn.Linear(64, 32), nn.ReLU(),
                          nn.Linear(32, 1))
    opt = torch.optim.Adam(model.parameters(), lr=lr)
    g = torch.Generator().manual_seed(seed)
    for _ in range(epochs):
        perm = torch.randperm(len(Xl), generator=g)
        for st in range(0, len(perm), batch):
            b = perm[st:st + batch]
            loss = ltr_loss(model(Xl[b]).squeeze(-1), Yl[b], Ml[b], kind)
            opt.zero_grad()
            loss.backward()
            opt.step()
    return model

def score_df(model, df):
    with torch.no_grad():
        x = torch.as_tensor(((df[FEATS].values - mu) / sd).astype(np.float32))
        return model(x).squeeze(-1).numpy()

Xl, Yl, Ml = to_lists(tr)
ltr = {}
for kind in ("pointwise", "ranknet", "lambdarank", "listwise"):
    ltr[kind] = train_ltr(kind, Xl, Yl, Ml)
    te["s_" + kind] = score_df(ltr[kind], te)
    print(f"MLP {kind:>10}: NDCG@10 {ndcg_table(te, 's_' + kind, truth_C):.4f}")
```

```output
MLP  pointwise: NDCG@10 0.1034
MLP    ranknet: NDCG@10 0.1196
MLP lambdarank: NDCG@10 0.1187
MLP   listwise: NDCG@10 0.1192
```

Same network, same features, same data — and the objective is worth 0.016 NDCG. The pointwise MLP
(0.1034) is the worst model in the chapter so far, below plain iALS order; the three
within-list losses all land between 0.1187 and 0.1196, about 5% above iALS order. The fix was not
more capacity but telling the model what the metric ignores.

The three list-aware losses sit within 0.001 of each other — differences you should not believe
without ch. 2's paired bootstrap — and that is the usual finding with binary labels and short
lists. LambdaRank's top-heavy weighting earns its reputation
with graded relevance and long lists, where most pairs sit far below the cutoff and RankNet wastes
effort on them. Its real strength in practice is LambdaMART: the same gradient driving a GBDT,
which is why "LightGBM with `lambdarank`" is the default ranker in industry and on Kaggle.

## End to end: does the ranker pay for itself?

plausible-looking wrong items to promote. The two effects pull in opposite directions, so the
right pile size is an empirical question. Below, the rankers trained at $n = 50$ per source are
applied unchanged to piles built with 10 to 100 per source.

## Leakage: the bug that makes a ranker look brilliant

Leakage in a ranker is rarely as crude as a label column. It is usually a feature computed by a
"nightly snapshot" job over the *whole* log, which for training rows means over the label window
too. Here the bug is exactly that: candidates and retrieval scores are built properly from window
A, but the user genre affinities and item popularity/trend statistics are computed from A+B — so
for training rows they already contain the clicks the model is asked to predict.

The check is the one that would be run in practice: hold out 20% of training users, measure NDCG
on them (the offline number a team would report), then measure on the future window C, where the
features are necessarily computed honestly.

```python
# the bug: user and item aggregates come from a snapshot of the whole log (through t2)
tr_leak = feature_table(src_A, hist_A, t1, users_tr, truth_B, agg_hist=hist_AB)
val_users = set(users_tr[np.random.default_rng(0).random(len(users_tr)) < 0.2])
results = []
for name, table in (("clean", tr), ("leaky", tr_leak)):
    fit_rows = ~table["user"].isin(val_users)
    m = HistGradientBoostingClassifier(max_iter=300, learning_rate=0.05, random_state=0)
    m.fit(table.loc[fit_rows, FEATS], table.loc[fit_rows, "label"])
    val = table[~fit_rows].copy()
    val["s"] = m.predict_proba(val[FEATS])[:, 1]
    te["s_tmp"] = m.predict_proba(te[FEATS])[:, 1]
    results.append((name, ndcg_table(val, "s", truth_B), ndcg_table(te, "s_tmp", truth_C)))
print(f"{'features':>9} {'offline val NDCG@10':>20} {'future test NDCG@10':>20}")

```

```output
    clean               0.1143               0.1067
```

The leaky model reports 0.1511 offline — a 32% jump that would get the change shipped — and then

feature no longer contains the future. The offline number was not optimistic; it was measuring a

The defence is structural, not a check you remember to run: build every feature with an explicit
`as_of` timestamp (here `now = t1` and `hist_A`), take labels strictly after it, and make the
training-table builder the *same function* that serves features at request time. Production
systems do this with a feature store that supports point-in-time joins. Note the clean model also
drops from 0.1143 offline to 0.1067 on window C: some gap between validation and the future is
normal drift, and it is the size of the gap, not its existence, that signals leakage.

## Re-ranking: rules and diversity after the model

The ranker scores each item on its own, so ten near-duplicates with high scores all make the top
10. A third, cheap stage fixes the *list* as a whole: business rules (no more than three items of
one genre, filter out-of-stock, boost a promotion) and diversity re-ranking. The standard
diversity method is **maximal marginal relevance** (MMR, Carbonell & Goldstein 1998): build the
list greedily, each time picking the item that balances its own relevance against its similarity
to what is already chosen,

$$
i^\star = \arg\max_{i \in C_u \setminus S}\; \lambda\,\mathrm{rel}(i) - (1-\lambda)\max_{j \in S}\,\mathrm{sim}(i, j),
$$

where $S$ is the list built so far, $\mathrm{rel}$ is the ranker's score scaled to $[0, 1]$,
$\mathrm{sim}$ is cosine similarity of iALS item vectors, and $\lambda \in [0, 1]$ sets the
trade-off ($\lambda = 1$ is pure ranker order).

```python
V_n = src_AB["V"] / (np.linalg.norm(src_AB["V"], axis=1, keepdims=True) + 1e-9)

def mmr(items, rel, lam, k=10):
    chosen, pool = [], list(range(len(items)))
    while pool and len(chosen) < k:
        if chosen:
            sim = (V_n[items[pool]] @ V_n[items[chosen]].T).max(1)
        else:
            sim = np.zeros(len(pool))
        best = pool[int(np.argmax(lam * rel[pool] - (1 - lam) * sim))]
        chosen.append(best)
        pool.remove(best)
    return items[chosen]

def genre_cap(items, rel, cap=3, k=10):
    out, count = [], np.zeros(6, int)
    for i in items[np.argsort(-rel)]:
        if count[genre[i]] < cap:
            out.append(i)
            count[genre[i]] += 1
        if len(out) == k:
            break
    return np.array(out)

groups = {u: (g["item"].values, g["s_lambdarank"].values) for u, g in te.groupby("user")}
print(f"{'policy':>18} {'NDCG@10':>8} {'genres in top-10':>17} {'intra-list sim':>15}")
policies = [("ranker order", lambda it, s: it[np.argsort(-s)][:10])]
policies += [(f"MMR lambda={lam}", lambda it, s, lam=lam: mmr(it, (s - s.min()) / (s.max() - s.min()), lam))
             for lam in (0.9, 0.7, 0.5)]
policies += [("cap 3 per genre", genre_cap)]
for name, pol in policies:
    nd, ng, ils = [], [], []
    for u in users_te:
        top = pol(*groups[u])
        nd.append(ndcg_at_10(top, truth_C[u]))
        ng.append(len(set(genre[top])))
        sims = V_n[top] @ V_n[top].T
        ils.append((sims.sum() - len(top)) / (len(top) * (len(top) - 1)))
    print(f"{name:>18} {np.mean(nd):>8.4f} {np.mean(ng):>17.2f} {np.mean(ils):>15.3f}")
```

```output
      ranker order   0.1187              3.01           0.658
    MMR lambda=0.9   0.1189              3.26           0.643
    MMR lambda=0.7   0.1162              3.86           0.599
    MMR lambda=0.5   0.1071              4.61           0.532
   cap 3 per genre   0.1087              4.57           0.560
```

The re-ranker now runs on the LambdaRank MLP's scores (0.1187 in ranker order). A light touch of
MMR ($\lambda = 0.9$) is free: 3.26 genres instead of 3.01, lower intra-list similarity, and NDCG
unchanged at 0.1189. Push harder and you pay — $\lambda = 0.5$ reaches 4.61 genres but loses
0.0116 NDCG. The blunt business rule is interesting: "at most 3 per genre" gets almost the same
diversity as MMR at 0.5 (4.57 genres) for less NDCG cost (0.1087 against 0.1071), because it only
intervenes when a genre actually floods the list.

Offline NDCG cannot settle how much diversity to buy. It rewards predicting the next click, and
the next click is concentrated in the user's habitual genres; the value of diversity — discovery,
long-term retention, not boring the user — shows up only online, in experiments and bandit-style exploration (ch. 11). The job of
this table is to price each policy so the online test compares sensible options.

## Try it Yourself

A self-contained sandbox for the four losses. Each "user" has 40 candidates with 8 features and
graded labels 0–3; the labels also depend on a per-list offset the features cannot see (some users
are simply more enthusiastic), and on a feature interaction a linear scorer cannot represent.

```python
import numpy as np
import torch
import torch.nn.functional as F

torch.manual_seed(0)
torch.set_num_threads(1)
rng = np.random.default_rng(0)
n_q, L, d = 400, 40, 8                     # 400 queries (users), 40 candidates each, 8 features
w_true = rng.normal(0, 1, d)
X = rng.normal(0, 1, (n_q, L, d))
offset = rng.normal(0, 2.0, (n_q, 1))     # per-list effect the features cannot see (a user's mood)
signal = X @ w_true + 0.8 * X[..., 1] * X[..., 2] + rng.normal(0, 1.0, (n_q, L))
thr = np.quantile(signal + offset, [0.80, 0.93, 0.98])                  # one global grading scale
y = sum((signal + offset > t).astype(np.float32) for t in thr)
keep = y.max(1) > 0                                                     # lists with something relevant
X, y = X[keep], y[keep]
X, y = torch.tensor(X, dtype=torch.float32), torch.tensor(y)
Xtr, ytr, Xte, yte = X[:250], y[:250], X[250:], y[250:]
disc_k = 1 / torch.log2(torch.arange(L) + 2.0)

def ndcg10(s, y):
    top = torch.argsort(s, dim=1, descending=True)[:, :10]
    dcg = ((2 ** torch.gather(y, 1, top) - 1) * disc_k[:10]).sum(1)
    idcg = ((2 ** torch.sort(y, 1, descending=True).values[:, :10] - 1) * disc_k[:10]).sum(1)
    return float((dcg / idcg).mean())

def fit(kind, steps=300):
    w = torch.zeros(d, requires_grad=True)
    opt = torch.optim.Adam([w], lr=0.05)
    gain = 2 ** ytr - 1
    for _ in range(steps):
        s = Xtr @ w
        diff = s[:, :, None] - s[:, None, :]
        pair = ytr[:, :, None] > ytr[:, None, :]
        if kind == "pointwise (regress grade)":
            loss = F.mse_loss(s, ytr)
        elif kind == "listwise":
            p = gain / gain.sum(1, keepdim=True)
            loss = -(p * F.log_softmax(s, 1)).sum(1).mean()
        else:
            wt = torch.ones_like(diff)
            if kind == "lambdarank":
                with torch.no_grad():
                    disc = disc_k[torch.argsort(torch.argsort(-s, 1), 1)]
                    wt = ((gain[:, :, None] - gain[:, None, :]) * (disc[:, :, None] - disc[:, None, :])).abs()
            loss = (F.softplus(-diff) * wt)[pair].mean()
        opt.zero_grad()
        loss.backward()
        opt.step()
    return ndcg10(Xte @ w.detach(), yte)

print(f"{len(X)} lists kept | random order: NDCG@10 {ndcg10(torch.rand(len(yte), L), yte):.4f}")
for kind in ("pointwise (regress grade)", "ranknet", "lambdarank", "listwise"):
    print(f"{kind:>26}: NDCG@10 {fit(kind):.4f}")
```

```output
 pointwise (regress grade): NDCG@10 0.8334
                   ranknet: NDCG@10 0.8272
                lambdarank: NDCG@10 0.8362
                  listwise: NDCG@10 0.8405
```

All four losses land between 0.827 and 0.841, far above random (0.1871) and close to each
other. With a linear scorer the model is just a direction $\mathbf{w}$, and the unobserved per-list
offset is independent of the features, so it adds noise to the pointwise regression without
biasing the direction — every loss finds roughly the same $\mathbf{w}$. That is why the losses
diverged on the real table only once the user-level feature and an MLP with capacity to fit it
were present.

Try breaking the independence: make the offset correlated with a feature
(`offset = 2.0 * X[..., 3].mean(1, keepdims=True)`), so a pointwise model can "explain" the
offset with feature 3 and mis-weight it within lists. Then replace the linear scorer with a small
MLP, or score NDCG@3 instead of @10, and see whether LambdaRank's top-heavy weights start to pay.
