## Floating-point is not real arithmetic

Computers can't store most numbers exactly. They keep about 7 significant digits (float32)
or about 16 (float64) and round the rest away. Usually that's fine. But some calculations
magnify those tiny rounding errors until the answer is garbage — and this chapter is about
spotting and avoiding them.

Every number stored in float32 or float64 is a finite approximation. The gaps between representable numbers grow with magnitude (relative spacing $\approx 10^{-7}$ for float32, $10^{-16}$ for float64). Most bugs in ML code come from forgetting this.

> **Picture it:** floats are a ruler whose tick marks get further apart as numbers get
> bigger. Near 1 the ticks are a hair apart; near a billion they're 64 apart in float32. Every result snaps to the nearest tick.

## The condition number

Some problems are touchy: nudge the input a hair and the answer swings wildly. The
**condition number** measures that touchiness. A large one means rounding errors in the
input become large errors in the output.

The **condition number** $\kappa(A) = \sigma_{\max} / \sigma_{\min}$ measures how much a linear system $Ax = b$ amplifies input perturbations:

$$
\frac{\|\delta x\|}{\|x\|} \le \kappa(A) \frac{\|\delta b\|}{\|b\|}
$$

> **In plain words:** the relative error in the answer $x$ can be up to $\kappa$ times the
> relative error in the data $b$. $\delta x$ and $\delta b$ ("delta") mean "the small change
> in". $\sigma_{\max}$ and $\sigma_{\min}$ are the largest and smallest singular values
> (ch. 5) — the most and least the matrix stretches anything.

A perturbation of relative size $\varepsilon$ in $b$ can cause a perturbation of size $\kappa(A) \cdot \varepsilon$ in $x$. With float64 ($\varepsilon_{\text{mach}} \approx 10^{-16}$) and $\kappa = 10^{10}$, you lose 10 digits of accuracy — only 6 digits remain.

Rule of thumb: you lose about $\log_{10} \kappa$ digits.

```python
import numpy as np

def make_hilbert(n):
    return np.array([[1.0 / (i + j + 1) for j in range(n)] for i in range(n)])

for n in [5, 8, 10]:
    H = make_hilbert(n)
    kappa = np.linalg.cond(H)
    # Solve Hx = b with known solution
    x_true = np.ones(n)
    b = H @ x_true
    x_solved = np.linalg.solve(H, b)
    err = np.max(np.abs(x_solved - x_true))
    print(f"Hilbert {n}×{n}: κ={kappa:.2e}  max error={err:.2e}")
```

```output
Hilbert 5×5: κ=4.77e+05  max error=2.09e-12
Hilbert 8×8: κ=1.53e+10  max error=1.31e-07
Hilbert 10×10: κ=1.60e+13  max error=2.43e-05
```

The **Hilbert matrix** (entries $1/(i + j + 1)$) is the classic ill-conditioned example. As
$n$ goes from 5 to 10, $\kappa$ climbs from $5 \times 10^5$ to $1.6 \times 10^{13}$, and the
error in a problem whose exact answer is all ones climbs from $10^{-12}$ to $10^{-5}$ — the
rule of thumb in action ($16 - 13 = 3$ digits left would predict an error near $10^{-3}$;
it's an upper bound, and here reality is kinder).

As the condition number grows, the solution error grows proportionally.

> **Watch out:** ill-conditioning lives in the *problem*, not the algorithm. No solver can
> recover digits that rounding already destroyed. The cures are mathematical: rescale
> features, add regularization ($+\varepsilon I$, ch. 7), or reformulate.

## Catastrophic cancellation

Subtracting two numbers that are almost equal wipes out the digits they share, and what's
left is mostly rounding noise. That's **catastrophic cancellation**.

Subtracting two nearly equal floating-point numbers destroys significant digits:

```python
import numpy as np

# float32 has ~7 decimal digits of precision
x = np.float32(1.0)
eps = np.float32(1e-7)

result = (x + eps) - x
print(f"float32: (1 + 1e-7) - 1 = {result}")
print(f"Expected: 1e-7 = {1e-7}")
print(f"Relative error: {abs(float(result) - 1e-7) / 1e-7:.1%}")

# float64 is fine here
result64 = (np.float64(1.0) + np.float64(1e-7)) - np.float64(1.0)
print(f"\nfloat64: (1 + 1e-7) - 1 = {result64}")
```

```output
float32: (1 + 1e-7) - 1 = 1.1920928955078125e-07
Expected: 1e-7 = 1e-07
Relative error: 19.2%

float64: (1 + 1e-7) - 1 = 1.0000000005838672e-07
```

In float32, $1 + 10^{-7}$ isn't representable: the nearest float32 above 1 is
$1 + 1.19 \times 10^{-7}$ (one **machine epsilon**, the tick spacing at 1). So the sum snaps to
that tick, and subtracting 1 gives $1.19 \times 10^{-7}$ instead of $10^{-7}$ — a 19% error
from a single addition. float64 gets it right to about 8 digits (`1.0000000005838672e-07`: the
rounding error of the sum shows up in the 9th digit).

Float32 can't hold the `1e-7` accurately — it snaps to the nearest tick and comes back 19%
wrong; anything below half a tick (say `5e-8`) is dropped entirely, a 100% error. Use float64 for accumulation, or restructure the computation.

> **In plain words:** "big + tiny − big" is dangerous: the tiny part gets rounded while it's
> sitting next to the big one. Rearranging to "tiny + (big − big)" or working with
> differences directly avoids it.

## The log-sum-exp trick

$e^{1000}$ is far too big for any float — it overflows to infinity. But $\log(e^{1000} +
e^{1001} + e^{1002})$ is a perfectly ordinary number, about 1002.4. The trick is to never
form the giant numbers in the first place.

Computing $\log \sum_i e^{x_i}$ is the core of softmax, cross-entropy, and log-partition functions. Naive computation overflows for large $x_i$:

```python
import numpy as np

logits = np.array([1000.0, 1001.0, 1002.0], dtype=np.float64)

# Naive: overflow
try:
    naive = np.log(np.sum(np.exp(logits)))
    print(f"Naive log-sum-exp: {naive}")
except:
    print("Naive: overflow exception")

naive_val = np.log(np.sum(np.exp(logits)))
print(f"Naive result: {naive_val}")   # will be inf
```

```output
Naive log-sum-exp: inf
Naive result: inf
```

Both lines print `inf`, and the `except` branch never runs: NumPy doesn't raise an exception
on overflow — it returns `inf` (and a `RuntimeWarning` on stderr) and carries on. The
largest float64 is about $1.8 \times 10^{308}$, roughly $e^{709}$, so $e^{1000}$ is hopeless.

> **Watch out:** silent `inf` and `nan` are worse than crashes: they flow through the rest of
> the computation and surface many steps later as a `nan` loss. `np.seterr(all='raise')`
> turns them into exceptions while debugging.

The **log-sum-exp trick** subtracts $c = \max(x)$ before exponentiation, keeping all values in range:

$$
\log \sum_i e^{x_i} = c + \log \sum_i e^{x_i - c}
$$

> **In plain words:** factor out the biggest term: $\sum_i e^{x_i} = e^{c} \sum_i e^{x_i - c}$,
> and the log of $e^c$ is just $c$. After the shift, every exponent is $\le 0$, so every
> $e^{x_i - c}$ is between 0 and 1 — no overflow — and the largest one is exactly 1, so the sum
> can't underflow to zero either.

```python
import numpy as np

def log_sum_exp(x):
    c = x.max()
    return c + np.log(np.sum(np.exp(x - c)))

logits = np.array([1000.0, 1001.0, 1002.0])
print(f"Stable log-sum-exp: {log_sum_exp(logits):.6f}")
print(f"Expected (by hand): {1002 + np.log(np.exp(-2)+np.exp(-1)+np.exp(0)):.6f}")
```

```output
Stable log-sum-exp: 1002.407606
Expected (by hand): 1002.407606
```

The stable version returns 1002.407606, matching the hand calculation $1002 + \log(e^{-2} +
e^{-1} + e^{0})$. The answer is a bit above the largest input, as log-sum-exp always is: it's a
"soft maximum".

### Numerically stable softmax

Apply the same trick:

```python
import numpy as np

def stable_softmax(x):
    x_shift = x - x.max()        # subtract max; doesn't change output
    e = np.exp(x_shift)
    return e / e.sum()

logits = np.array([3.0, 1.0, 0.2, 1000.0])
probs = stable_softmax(logits)
print("Probabilities:", np.round(probs, 6))
print("Sum to 1:", np.isclose(probs.sum(), 1.0))
```

```output
Probabilities: [0. 0. 0. 1.]
Sum to 1: True
```

The logit 1000 is so far above the others ($e^{-997}$ underflows to 0) that it takes all the
probability, and the result still sums to 1. Without the shift, `np.exp(1000.0)` would be `inf`
and the output `nan`.

The last logit dominates, so probability mass concentrates there — correct without overflow.

## Never invert a matrix

Computing $A^{-1}$ and then multiplying is like solving an equation by first working out a
whole table of answers you don't need. It's more work, and every extra step adds rounding.

`np.linalg.inv(A) @ b` computes $A^{-1}$ explicitly. This is:
1. **Slower** than `np.linalg.solve(A, b)` — roughly 3× for large matrices.
2. **Less accurate** — the inversion itself introduces rounding errors that `solve` avoids.

```python
import numpy as np

rng = np.random.default_rng(0)
n = 200
A = rng.standard_normal((n, n))
A = A.T @ A + n * np.eye(n)   # make PD
b = rng.standard_normal(n)
x_true = np.linalg.solve(A, b)   # reference

# Method 1: solve (LU decomposition internally)
x_solve = np.linalg.solve(A, b)

# Method 2: invert then multiply
x_inv = np.linalg.inv(A) @ b

err_solve = np.max(np.abs(A @ x_solve - b))
err_inv   = np.max(np.abs(A @ x_inv - b))

print(f"solve residual : {err_solve:.2e}")
print(f"inv residual   : {err_inv:.2e}")
print(f"solve is more accurate: {err_solve <= err_inv}")
```

```output
solve residual : 3.55e-15
inv residual   : 2.00e-15
solve is more accurate: False
```

A surprise worth understanding: here `inv` happens to give the *smaller* residual, so the
check prints `False`. This matrix ($A^TA + 200I$) is extremely well-conditioned, so both
methods are at the rounding floor ($10^{-15}$) and which one wins is luck. The accuracy
argument against `inv` is about **ill-conditioned** matrices: on the Hilbert matrix in the
Exercise below, `solve`'s residual is about 1000× smaller. The speed argument holds always.

## Float traps summary

```python
import numpy as np

# 1. Never compare floats with ==
a = 0.1 + 0.2
print(f"0.1 + 0.2 == 0.3 : {a == 0.3}")
print(f"np.isclose(0.1+0.2, 0.3): {np.isclose(a, 0.3)}")

# 2. NaN propagates silently
x = np.array([1.0, np.nan, 3.0])
print(f"np.mean([1, nan, 3]) = {np.mean(x)}")    # nan!
print(f"np.nanmean           = {np.nanmean(x)}")  # use nanmean

# 3. inf arithmetic
print(f"1/0 in numpy: {np.float64(1)/0}")        # inf (no exception)
print(f"inf - inf  : {np.inf - np.inf}")         # nan
```

```output
0.1 + 0.2 == 0.3 : False
np.isclose(0.1+0.2, 0.3): True
np.mean([1, nan, 3]) = nan
np.nanmean           = 2.0
1/0 in numpy: inf
inf - inf  : nan
```

Three habits. Compare floats with a tolerance (`np.isclose`), never `==`: $0.1$ and $0.2$
have no exact binary form, so their sum is `0.30000000000000004`. A single `nan` poisons a
whole mean — use the `nan`-aware functions when missing values are possible. And NumPy turns
$1/0$ into `inf` and $\infty - \infty$ into `nan` without complaint.

## Recap in plain words

- Floats keep about 7 (float32) or 16 (float64) significant digits; every result is rounded.
- The condition number $\kappa$ says how much a problem magnifies errors; you lose about
  $\log_{10} \kappa$ digits.
- Subtracting nearly equal numbers destroys precision (catastrophic cancellation).
- Log-sum-exp: subtract the max before exponentiating; softmax does the same.
- Prefer `solve` over `inv`: always faster, and much more accurate on ill-conditioned
  matrices.
- Never compare floats with `==`; watch for silent `inf` and `nan`.

## Try it Yourself

```python
import numpy as np

# Compute log-partition function for a 10-class classifier output
# log Z = log sum_i exp(logit_i)
rng = np.random.default_rng(0)
logits = rng.standard_normal(10) * 10   # large range

def log_sum_exp(x):
    c = x.max()
    return c + np.log(np.sum(np.exp(x - c)))

log_Z = log_sum_exp(logits)
print("Logits:", np.round(logits, 2))
print("log Z (stable):", round(log_Z, 6))
print("Max logit:     ", round(logits.max(), 6))
print("log Z > max:   ", log_Z > logits.max())   # always true: log(sum) > log(max)
```

```output
Logits: [  1.26  -1.32   6.4    1.05  -5.36   3.62  13.04   9.47  -7.04 -12.65]
log Z (stable): 13.069158
Max logit:      13.04
log Z > max:    True
```

`log Z` (13.069) is just a little above the largest logit (13.04), because the second-largest
logit (9.47) is far enough below that it adds only $\log(1 + e^{-3.6} + \dots) \approx 0.03$.
When one logit dominates, log-sum-exp is almost exactly the max — that's why it's called a
soft maximum. Try `* 100` instead of `* 10` and watch `log Z` and the max become identical to
six decimals.

```python
import numpy as np

# Hilbert matrix: notoriously ill-conditioned
n = 5
H = np.array([[1.0/(i+j+1) for j in range(n)] for i in range(n)])
x_true = np.ones(n)
b = H @ x_true

print(f"Condition number κ(H) = {np.linalg.cond(H):.2e}")

x_solve = np.linalg.solve(H, b)
x_inv   = np.linalg.inv(H) @ b

res_solve = np.max(np.abs(H @ x_solve - b))
res_inv   = np.max(np.abs(H @ x_inv   - b))
err_solve = np.max(np.abs(x_solve - x_true))
err_inv   = np.max(np.abs(x_inv   - x_true))

print(f"solve — residual: {res_solve:.2e}  solution error: {err_solve:.2e}")
print(f"inv   — residual: {res_inv:.2e}  solution error: {err_inv:.2e}")
```

`np.linalg.solve` produces a smaller residual because it uses LU decomposition with pivoting rather than explicitly forming $H^{-1}$, which accumulates more rounding error.
For the 5×5 Hilbert matrix the residual from `solve` is around $10^{-16}$ and from `inv` around
$10^{-13}$, and the solution error is about 20× smaller with `solve`. At 10×10 the gap grows to
a residual ratio of about $10^{11}$. (**Pivoting** means reordering rows during elimination so
you never divide by a tiny number.)

## Under the Trench

Rare and advanced topics you should at least know the name of.

- **KKT conditions** — Lagrange multipliers (ch. 11) generalised to inequality constraints $h_i(x) \le 0$: the complementary slackness condition $\mu_i h_i(x^*) = 0$ (a multiplier is zero unless its constraint is "touching") and dual feasibility $\mu_i \ge 0$ must hold at any constrained minimum. The dual formulation behind SVMs comes directly from KKT.
- **Second-order / Newton & quasi-Newton (L-BFGS)** — Newton's step $\Delta w = -[\nabla^2 f]^{-1} \nabla f$ uses curvature (the Hessian, ch. 3) to take exact steps on quadratics. L-BFGS approximates the inverse Hessian from the last $m$ gradient differences, requiring only $O(md)$ memory instead of $O(d^2)$.
- **Automatic differentiation internals** — forward mode propagates $\dot{x}$ alongside $x$ (cheap for few inputs, many outputs); reverse mode backpropagates adjoints $\bar{x}$ from output to inputs (cheap for many inputs, one output — exactly what ML needs). The dual-number trick implements forward AD by augmenting scalars with an infinitesimal component $x + \dot{x}\varepsilon$.
- **Proximal & subgradient methods** — when $f$ is non-smooth (L1 penalty, hinge loss), the gradient doesn't exist at kinks. The proximal operator for L1 is soft-thresholding: $\text{prox}_{\lambda\|\cdot\|_1}(v)_i = \text{sign}(v_i)\max(|v_i|-\lambda, 0)$ — shrink every entry toward zero by $\lambda$, and snap small ones to exactly zero. Subgradient methods use any element of the subdifferential (any slope that fits under the kink).
- **Conjugate gradient** — solves $Ax=b$ for symmetric PD $A$ in at most $d$ iterations (in exact arithmetic) without forming $A^{-1}$; in practice converges in $O(\sqrt{\kappa})$ iterations; the workhorse solver inside many optimisation libraries for large systems.
- **Matrix factorizations (QR, Cholesky, LU)** — QR solves least-squares stably; Cholesky solves PD systems 2× faster than LU (ch. 7); LU with partial pivoting solves general square systems; all avoid the accuracy and cost penalty of explicit matrix inversion.
- **Tensor/Einstein notation & contractions** — `np.einsum('ij,jk->ik', A, B)` is matrix multiply; `'bij,bjk->bik'` is batched matrix multiply; `'bik,bjk->bij'` is a batch of $A B^T$ products (every row of one against every row of the other). Any linear contraction over any subset of indices is expressible as an einsum string, eliminating explicit loops.
